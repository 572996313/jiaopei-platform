# 教培平台产品架构与菜单重组方案

## 1. 背景与目标

针对客户提出的以下反馈：

- 系统设计太平，没有主次
- 菜单功能不像一个完整产品
- 基础信息不够，功能体现不出来
- 系统模块像平铺页面集合，不像教务工作台

本方案的目标不是单纯调整视觉，而是把当前系统从“功能集合”重组为“围绕教务主线的工作台产品”。

核心目标：

1. 让用户一眼看懂系统主次
2. 让基础信息、业务执行、系统设置分层清晰
3. 让排课与课次执行成为系统核心价值主线
4. 为后续请假、补课、调课、回查、经营延展留出清晰结构

## 2. 当前问题诊断

当前系统的核心问题不是“页面少”，而是“产品架构没有把教培主线组织出来”。

### 2.1 当前菜单过于平铺

当前一级菜单基本为：

- 工作台
- 系统管理
- 校区管理
- 教师管理
- 学员管理
- 班级管理
- 排课与课表

问题：

- 业务菜单和系统底座几乎同级，主次感弱
- 看不出“先配什么，再做什么”
- 用户不知道日常核心入口在哪里

### 2.2 页面命名大而空，页面承接范围偏窄

典型问题：

- “学员管理”当前更接近报名/入班关系，不是完整学员档案
- “班级管理”当前更接近班级学员关系，不是班级主档
- “排课与课表”开始承接了点名，但还没有升级为完整执行中心

结果：

- 客户会觉得页面名称很大，但功能只承接一小段
- 容易形成“鸡肋”“不像产品”的印象

### 2.3 基础主数据层不完整

当前已有部分基础数据：

- 机构、校区、教室、学期、时间段
- 教师、学员
- 班级学员关系
- 排课课次与点名

但缺少完整主数据层：

- 课程分类
- 课程
- 班型
- 班级主档
- 班级教师关系
- 教师授课能力
- 家长联系人
- 统一业务状态字典

### 2.4 工作台没有成为业务入口

首页还没有成为“今日教务工作台”，没有承接真正的日常动作：

- 今日课次
- 待点名
- 请假待处理
- 调课/补课待确认
- 教师或教室异常

## 3. 新的产品架构原则

后续系统不再按“平铺功能模块”推进，而改成三层结构：

1. 工作台层：告诉用户今天先做什么
2. 主数据层：保证教务业务能跑起来
3. 执行与回查层：承接系统真正的核心价值

同时明确一条主业务线：

`基础资料 -> 班级成班 -> 排课生成课次 -> 课次执行 -> 点名/请假/补课/调课 -> 数据回查`

## 4. 新菜单树方案

建议一级菜单调整为：

### 4.1 工作台

- 今日教务
- 待办中心
- 课次执行看板

定位：

- 系统首页
- 每日第一屏
- 教务老师日常入口

### 4.2 日常教务

- 排课管理
- 今日课表
- 课次执行
- 课次点名
- 请假管理
- 补课管理
- 调课管理
- 停课管理
- 结课处理

定位：

- 工作台之后的第一业务层
- 面向老师和教务每天高频使用
- 让客户一进系统就看到“今天要处理什么”

### 4.3 档案中心

- 机构与校区
- 教室与时间段
- 学期
- 课程分类
- 课程
- 班型
- 教师档案
- 学员档案
- 家长联系人

定位：

- 承接“开课前要先配什么”
- 承接“日常变动时依赖哪些主数据”
- 解决基础信息不够的问题

### 4.4 班级与教学

- 班级主档
- 班级教师
- 班级学员
- 报名与入班

定位：

- 承接“谁在什么班、谁来教、班是否可开”

### 4.5 数据回查

- 考勤回查
- 课次台账
- 班级出勤
- 教师课次回查

定位：

- 从“录入工具”升级为“管理工具”
- 支撑后续重台账页面建设

### 4.6 系统设置

- 用户
- 角色
- 菜单权限
- 字典

定位：

- 平台底座
- 放在最后
- 不再与业务主线抢主视觉

## 5. 页面职责重定义

为了避免“大标题、小能力”，建议将当前页面职责收口并重命名。

### 5.1 当前页面与目标职责映射

| 当前页面 | 当前问题 | 调整后归属 | 调整后建议名称 |
|---|---|---|---|
| 工作台 | 还偏静态占位 | 工作台 | 今日教务 |
| 校区管理 | 承载过多基础信息 | 档案中心 | 机构与校区 |
| 教师管理 | 更像教师档案入口 | 档案中心 | 教师档案 |
| 学员管理 | 当前更接近报名/关系承接 | 班级与教学 或 档案中心 | 报名与入班 / 学员档案 |
| 班级管理 | 当前更接近班级学员关系 | 班级与教学 | 班级学员 |
| 排课与课表 | 已承接点名，但定位不够强 | 日常教务 | 排课与执行中心 |
| 系统管理 | 位置过前 | 系统设置 | 系统设置 |

### 5.2 页面命名原则

后续命名遵循两条原则：

1. 页面名字要真实反映当前承接范围
2. 业务页面尽量使用业务语言，不使用技术实体语言

例如：

- 如果当前只承接“报名与入班”，就不要先叫“完整学员管理”
- 如果当前只承接“班级学员关系”，就不要先叫“完整班级管理”

## 6. 首页工作台建议

首页必须从“展示页”改成“教务工作台”。

建议首页首批展示：

### 6.1 统计卡片

- 今日课次数
- 待点名课次数
- 已完成课次数
- 请假待处理数
- 调课待处理数
- 教师冲突数

### 6.2 今日重点列表

- 今日待点名课次
- 今日异常课次
- 待处理请假
- 待确认调课/补课

### 6.3 快捷入口

- 新增排课
- 今日课表
- 进入点名
- 班级学员调整

### 6.4 目标

首页要回答三个问题：

1. 今天有什么事要做
2. 哪个入口最重要
3. 当前业务有没有异常

## 7. 老师视角的产品设计原则

客户现在最在意的，不只是菜单顺序，而是系统要更像老师每天真正在用的产品，而不是一组后台页面。

### 7.1 先看今天要做什么，再看系统里有什么

老师进入系统时最关心的是：

- 今天上哪些课
- 哪些课待点名
- 哪些课有变动
- 哪个班请假了
- 哪个老师临时调课了
- 哪个班还能不能正常上

所以产品结构必须优先展示“今天的工作”，而不是先展示“系统都有哪些模块”。

### 7.2 系统要能承接变动，而不是只承接静态建档

教培的真实情况不是“数据录完就不变”，而是持续变化：

- 已成班后学员增减
- 已成班后老师变更
- 老师请假、代课、跨校区授课
- 班级人数变化影响是否继续开班
- 学员请假、补课、调课
- 同一个机构不同校区成班规则不同
- 同一个课程不同老师带班规则不同

所以产品不能只做“建一条记录”，而要做“记录变化、承接变化、让后续流程跟着变化调整”。

### 7.3 成班规则不能写死，必须支持多维差异

客户提到的重点非常关键：

> 成班的规则不一定一样，针对老师成班的有时候也不一样，而且可能是多个维度的。

这件事的产品理解应该是：

- 系统不能把成班规则写死成一条固定逻辑
- 必须允许“规则配置 + 状态判断 + 后续联动”

典型维度可能包括：

- 校区维度
- 课程维度
- 班型维度
- 教师维度
- 学员人数维度
- 学期维度
- 授课方式维度

举例：

- A 校区满 8 人成班，B 校区满 6 人成班
- 钢琴一对一和数学小班的成班逻辑不同
- 某些老师允许“先开班后补满”，某些老师不允许

### 7.4 前面规则变了，后面流程必须能跟着调整

系统后续不能只做“一个班级状态字段”，而是要逐步支持：

1. 成班规则配置
2. 班级状态自动/半自动判断
3. 成班变化对排课、点名、调课的联动提示
4. 特殊班级允许人工干预

### 7.5 先做“可承接变化”，再做“完全自动化”

首期不要急着把所有规则做成自动引擎。

正确路线是：

1. 先把关键规则对象化、配置化
2. 先让系统知道“这件事变了”
3. 再给出后续影响提示
4. 最后再逐步走向自动联动

也就是说，产品先做到：

- 能记录规则
- 能识别差异
- 能提示影响
- 能支持人工处理

### 7.2 P2 补强

## 9. 核心业务主线建设方向

### 8.1 当前主线

建议当前阶段聚焦：

`排课 -> 课次 -> 点名 -> 结课 -> 回查`

这条线已经最接近客户价值感知，且当前代码基础最好。

### 8.2 下一步主线扩展

在课次点名闭环基础上，优先扩：

- 请假
- 补课
- 调课
- 停课

原因：

- 这些能力和课次执行天然相邻
- 客户能明显感知“系统开始能管事”

## 10. 分阶段演进路线

### 阶段一：信息架构重组

目标：

- 先解决“太平、没主次、像页面集合”的问题

动作：

- 重构一级菜单
- 调整页面命名
- 重做首页为今日教务工作台
- 明确各页面当前承接边界

### 阶段二：补齐基础主数据

目标：

- 解决“基础信息不够”的结构性问题

动作：

- 课程分类、课程、班型
- 班级主档
- 班级教师
- 学员档案与家长联系人
- 成班规则配置

### 阶段三：做强排课与执行中心

目标：

- 形成真正的教务日常操作主战场

动作：

- 排课管理
- 课次点名
- 结课
- 请假/补课/调课/停课
- 变动影响提示
- 前置规则变动后的后续调整提示

### 阶段四：建设数据回查层

目标：

- 从记录工具升级为管理工具

动作：

- 考勤回查
- 课次台账
- 班级出勤统计
- 教师执行回查

### 阶段五：规则配置与联动深化

目标：

- 从“能承接变化”逐步升级为“能根据规则辅助判断和联动”

动作：

- 成班规则多维配置
- 特殊老师/班型规则差异支持
- 排课前规则校验提示
- 班级变动后的下游影响提示

### 阶段六：再考虑经营与家校延展

目标：

- 在教务主线稳定后，再进入更外围能力

动作：

- 续班/升班
- 收费联动
- 通知与家长端

## 11. 对客户的建议口径

建议对客户说明：

1. 当前不是简单“再补几个页面”，而是会把产品架构重组为教务工作台
2. 系统后续将分为：工作台、日常教务、档案中心、班级与教学、数据回查、系统设置
3. 首批优先把工作台、日常功能和档案层做扎实，让老师先能顺手用起来
4. 系统会逐步支持不同校区、班型、老师的规则差异，不把业务规则写死
5. 这样做的目标不是页面更多，而是让系统从“能录入”升级为“能组织日常教务工作”

## 12. 最终拍板结论

一句话总结：

`后续不再把系统当成平铺后台功能集合来补，而是按“老师每天真正在用的教务工作台产品”重新组织。`

具体执行上：

- 先改信息架构和首页
- 把工作台放第一、日常功能放前面、档案放后面、系统设置放最后
- 再补齐基础主数据和成班规则
- 再做强排课与执行主线
- 再补回查和规则联动
- 最后再考虑经营延展

这样才能真正解决客户“太平、没主次、基础不够、功能不突出”的问题。
