# 生产部署排障手册

现场部署失败时照着做。每条故障都按「先看什么 → 怎么判断 → 怎么修 → 怎么验证 → 怎么回滚」的顺序写，命令可以直接复制。

配套文档：[生产部署说明.md](生产部署说明.md)（正常部署流程）。

---

## 0. 三条铁律

1. **只修最上面那条错。** Compose 启动失败的日志是一串多米诺骨牌：`condition not reached`、`dependency failed to start`、`not started` 几乎永远是下游症状。真正的根因永远是日志里**第一条**报错。
2. **先备份，再改配置。**

   ```bash
   cd /mnt/software/jiaopei
   cp docker/docker-compose.prod.yml "docker/docker-compose.prod.yml.bak.$(date +%Y%m%d_%H%M%S)"
   cp docker/prod.env "docker/prod.env.bak.$(date +%Y%m%d_%H%M%S)"
   ```

   改完先校验语法，再启动：

   ```bash
   docker compose -f docker/docker-compose.prod.yml --env-file docker/prod.env config > /dev/null && echo "compose 语法 OK"
   ```

3. **改完必须验证。** 看 `ps` 的 STATUS/Health、看 backend 日志、调一次 `/api/health`。停在「命令返回 0」不算完。

---

## 1. 症状分诊表

| 日志里看到的第一条错 | 它真正的意思 | 去看 |
| --- | --- | --- |
| `pathspec '...' did not match any file(s) known to git` | git 不认识这个路径（文件未被跟踪 / 被 `.gitignore` 忽略） | [场景 A](#场景-a部署脚本-stash-报-pathspec) |
| `Bind for 127.0.0.1:6379 failed: port is already allocated` | 宿主机端口是全局资源，已经被别的容器占了 | [场景 B](#场景-b端口被占用) |
| `host not found in upstream "backend"` | 容器不在同一个 Docker 网络里，DNS 解析不到这个名字 | [场景 C](#场景-c在容器里解析不到另一个容器) |
| `dependency failed to start: container ... is unhealthy` / `condition not reached` | 上游服务没起来，下游被连带拖死——**不是**它自己的问题 | 往上找第一条错 |

## 场景 A：部署脚本 stash 报 pathspec

### 现象

```text
[WARN] 检测到本地有未提交的部署相关改动,先 stash 起来以免 git pull 失败
error: pathspec ':(prefix:0)docker/prod.env' did not match any file(s) known to git
```

脚本随即停止。

### 根因

`docker/prod.env` 被 `.gitignore` 忽略、git 不跟踪它。`git stash push -- <路径>` 只接受**受版本控制**的路径，哪怕列表里只有一项匹配不上，整条命令就失败。而 `prod.env` 本来也不会被 `git pull` 覆盖，根本不需要 stash。

### 判断

```bash
cd /mnt/software/jiaopei
git ls-files docker/prod.env          # 没有任何输出 = 未被跟踪
git check-ignore -v docker/prod.env   # 能打印出 .gitignore 第几行忽略了它
```

### 修复

**新版脚本（提交 `e7a179e` 及之后）已修复**：只 stash 受版本控制的文件，并做了存在性过滤。确认服务器上是新版：

```bash
grep -c "STASH_PATHS" docker/deploy.sh   # 输出 1 或以上 = 已是新版
```

如果服务器跑的还是旧脚本，直接运行永远卡在这一步，需要人工引导一次：

```bash
cd /mnt/software/jiaopei
# 1. 手动把真正受跟踪、且和远端有差异的部署文件暂存起来
git stash push -m "bootstrap" -- docker/deploy.sh
# 2. 拉到含修复的新脚本
git pull origin master
# 3. 恢复现场改动（有冲突就按提示手动解决）
git stash pop
# 4. 重新部署
./docker/deploy.sh "修复部署脚本"
```

### 验证 / 回滚

```bash
git stash list    # 应为空；若还留着 bootstrap 条目，说明第 3 步没成功
git status        # docker/deploy.sh 应显示为已修改（chmod +x 的权限位变化，正常）
```

回滚：`git stash list` 找到条目后 `git stash apply stash@{n}`。

> 建议顺手关掉权限位检测，避免 chmod 反复制造「本地已修改」：
> `git config core.fileMode false`

## 场景 B：端口被占用

### 现象

```text
Error starting userland proxy: listen tcp4 127.0.0.1:6379: bind: address already in use
Bind for 127.0.0.1:6379 failed: port is already allocated
```

随后 mysql、backend、frontend 一连串 `condition not reached` / `not started` —— 全是连锁反应。

### 根因

Docker 的端口映射最终要在宿主机上真实监听。宿主机端口是全局资源，两个容器不能抢同一个。服务器上往往已经有一套别人（1Panel、宝塔、系统服务）在跑的中间件。

### 判断

```bash
# 谁在监听 3306 / 6379
sudo ss -tlnp | grep -E ':(3306|6379)\b'

# 找出占用端口的容器
docker ps --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}' | grep -E '3306|6379'
```

看到类似输出就说明已有实例在跑：

```text
1Panel-redis-xxxx   Up 15 hours   127.0.0.1:6379->6379/tcp
1Panel-mysql-yyyy   Up 15 hours   127.0.0.1:3306->3306/tcp
```

### 两条路，选一条

**路线 1（推荐）：不要再起第二套，直接复用现有的 MySQL/Redis。**
跳转到 [场景 D](#场景-d复用宿主机上的-mysql--redis1panel-等)。

**路线 2（仅限确实需要独立实例）：改本项目容器映射到别的宿主机端口。**

```bash
cd /mnt/software/jiaopei
sed -i 's/^REDIS_PORT=.*/REDIS_PORT=6380/' docker/prod.env
sed -i 's/^MYSQL_PORT=.*/MYSQL_PORT=3307/' docker/prod.env
grep -E '^(REDIS|MYSQL)_PORT=' docker/prod.env
```

注意：改的只是**宿主机**端口，容器之间的连接仍走服务名 + 容器内 3306/6379，后端代码不用动。如果只是给本机调试用，建议同时把 `MYSQL_BIND` / `REDIS_BIND` 设成 `127.0.0.1`。

### 验证

```bash
docker compose -f docker/docker-compose.prod.yml --env-file docker/prod.env up -d
docker compose -f docker/docker-compose.prod.yml ps
```

`redis`、`mysql` 两行状态为 `Up (healthy)` 即可。

### 回滚

把 `docker/prod.env` 里的端口改回去（或恢复 `prod.env.bak.*`），`up -d` 重建即可。

## 场景 C：在容器里解析不到另一个容器

### 现象

```text
nginx: [emerg] host not found in upstream "backend" in /etc/nginx/conf.d/default.conf:17
```

frontend 反复重启。

### 根因

容器名/服务名解析**只发生在同一个 Docker 网络内**。而且：**一旦给服务显式写了 `networks:`，它就完全按声明来，不会自动保留 compose 默认网络。**

现场最典型的错法是：为了让 backend 能访问 1Panel 的 MySQL/Redis，给 backend 只写了 `networks: [1panel]`——backend 于是退出了默认网络，前端 nginx 的 `upstream backend` 就解析不到了。

### 判断

```bash
# 看两个容器分别在哪些网络里
docker inspect jiaopei-prod-backend  --format '{{range $k,$v := .NetworkSettings.Networks}}{{$k}} {{end}}'
docker inspect jiaopei-prod-frontend --format '{{range $k,$v := .NetworkSettings.Networks}}{{$k}} {{end}}'
```

两者必须有**至少一个共同网络**（通常是 `jiaopei_default`）。

### 修复

backend 同时挂两个网络——默认网络给前端用，外部网络给中间件用：

```yaml
services:
  backend:
    networks:
      - default   # compose 默认网络，frontend 的 upstream backend 靠它解析
      - 1panel    # 外部网络，用来访问 1Panel 的 mysql/redis

networks:
  1panel:
    external: true        # 已存在，compose 不负责创建
    name: 1panel-network  # 实际网络名，用 docker network ls 确认
```

改完：

```bash
docker compose -f docker/docker-compose.prod.yml --env-file docker/prod.env up -d
```

### 验证

```bash
# 从任意一个挂在 1panel-network 的临时容器验证 DNS
docker run --rm --network 1panel-network alpine getent hosts backend 2>/dev/null || true
docker compose -f docker/docker-compose.prod.yml ps
docker compose -f docker/docker-compose.prod.yml logs --tail=50 frontend
```

frontend 不再重启、日志里没有 `host not found in upstream` 即通过。

### 回滚

恢复 `docker-compose.prod.yml.bak.*`，`up -d`。

## 场景 D：复用宿主机上的 MySQL / Redis（1Panel 等）

目标架构：应用只跑 `backend` + `frontend` 两个容器，数据服务复用宿主机已有实例，不再重复维护一套。

```text
宿主机
├── 1panel-network
│   ├── 1Panel-mysql-xxxx   ←──┐
│   ├── 1Panel-redis-yyyy   ←──┤  按容器名直连（3306/6379 不再映射宿主机端口）
│   └── jiaopei-prod-backend ──┘
└── compose default 网络
    └── jiaopei-prod-frontend ──→ backend（服务名解析）
```

### D1. 动手前必做：先验证，再切连接

**凭据对不上就改配置，等于把问题往后推。** 下面三步全通过再往下走。

**① 找到真实容器名**（1Panel 的容器名后缀是随机的，**不要照抄文档里的示例**）：

```bash
docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Ports}}' | grep -Ei 'mysql|redis'
docker network inspect 1panel-network --format '{{range .Containers}}{{.Name}} {{end}}'
```

把后面命令里的 `<mysql容器名>`、`<redis容器名>` 换成上一步查到的名字。

**② 确认业务库和账号都在。** root 密码用 1Panel 面板里配置的那个（下面的 `$MYSQL_ROOT_PASSWORD` 只是变量名示例，**不要**把面板密码写进仓库文件）：

```bash
docker exec <mysql容器名> mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e "SHOW DATABASES;"
docker exec <mysql容器名> mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e "SELECT user,host FROM mysql.user WHERE user='jiaopei';"
docker exec <mysql容器名> mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e "SHOW GRANTS FOR 'jiaopei'@'%';"
```

要求：`jiaopei_platform`（业务库）和 `jiaopei_log`（操作留痕库）都存在；`jiaopei@'%'` 对两个库都有 `ALL PRIVILEGES`。缺库就按 [迁移/建库] 补，缺权限就补 `GRANT`。

**③ 确认 prod.env 里的密码能通过认证：**

```bash
cd /mnt/software/jiaopei
set -a; . docker/prod.env; set +a
docker exec <redis容器名> redis-cli -a "$REDIS_PASSWORD" ping        # 期望 PONG
docker exec <mysql容器名> mysql -u"$DB_USERNAME" -p"$DB_PASSWORD" -e "SELECT 1;"   # 期望返回 1
```

任何一步失败，先改 `docker/prod.env` 里的 `DB_PASSWORD` / `REDIS_PASSWORD`，**不要**先去改 compose。

### D2. 改 compose（四个动作，缺一不可）

编辑 `docker/docker-compose.prod.yml`（改前先按第 0 节备份）：

**① 删掉 `mysql:` 和 `redis:` 两个服务定义。**

**② backend 的连接地址指向真实容器名：**

```yaml
    environment:
      DB_HOST: <mysql容器名>
      DB_AUDIT_HOST: <mysql容器名>
      REDIS_HOST: <redis容器名>
```

`DB_PORT: 3306`、`REDIS_PORT: 6379` 不用动——这是**容器内**端口。

**③ 删掉 backend 的 `depends_on: mysql / redis`。** 服务都删了还留着引用，compose 校验会直接报错：

```yaml
    depends_on:
      mysql:                      # ← 整段删除
        condition: service_healthy
      redis:
        condition: service_healthy
```

**④ 网络打通：** backend 同时加入默认网络和 1Panel 的网络（原因见 [场景 C](#场景-c在容器里解析不到另一个容器)）。

```yaml
services:
  backend:
    networks:
      - default
      - 1panel

networks:
  1panel:
    external: true
    name: 1panel-network
```

> 同时关注 `docker/deploy.sh` 里的引用：新版脚本的健康检查已改为按编排中实际存在的服务动态判断；但数据库逻辑备份仍按 `jiaopei-prod-mysql` 容器名识别，复用外部 MySQL 时会静默跳过，见 [场景 E](#场景-e删掉-mysqlredis-服务后deploysh-的两处漏项)。

### D3. 启动并清掉孤儿容器

旧的 `jiaopei-prod-mysql` / `jiaopei-prod-redis` 已经不在 compose 定义里，属于**孤儿容器**：

```bash
docker compose -f docker/docker-compose.prod.yml --env-file docker/prod.env up -d --remove-orphans
```

> 删容器不会删数据：旧的 MySQL 数据在宿主机 bind mount（默认 `/mnt/software/jiaopei/data/mysql`）里，容器删了数据还在。确认新实例数据正常后，再决定是否清理旧数据目录。

### D4. 验证

```bash
# 1. 只剩预期的容器在跑
docker ps --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}'

# 2. backend 能解析到外部中间件（用临时容器测，避免依赖镜像里有没有 ping）
docker run --rm --network 1panel-network alpine getent hosts <mysql容器名>
docker run --rm --network 1panel-network alpine getent hosts <redis容器名>

# 3. backend 起来了，Flyway 迁移执行成功
docker compose -f docker/docker-compose.prod.yml logs --tail=100 backend | grep -iE 'flyway|started|error'

# 4. 接口可用
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:5757/api/health   # 期望 200（前端端口取 FRONTEND_PORT）
```

### D5. 回滚

```bash
cd /mnt/software/jiaopei
cp docker/docker-compose.prod.yml.bak.* docker/docker-compose.prod.yml
docker compose -f docker/docker-compose.prod.yml --env-file docker/prod.env up -d
```

回滚前确认 3306/6379 在宿主机上没被新方案占用（本方案不需要映射这两个端口，正常不会冲突）。

## 场景 E：删掉 mysql/redis 服务后，deploy.sh 的两处漏项

**这是最容易漏的一步**：compose 改完了、服务也起来了，但每次部署都报失败，而且数据库备份悄悄没了。

### E1. 健康检查永远失败 → 每次部署都 exit 2

旧版 `docker/deploy.sh` 的 `[5/9] 等待服务健康` 里写死了：

```bash
for SERVICE in mysql redis backend frontend; do
```

服务删掉后，`docker compose ps mysql` 拿不到状态，循环空等满 180 秒，最后 `ALL_HEALTHY=false`，脚本 `exit 2`。**服务其实是好的，只是检查对象错了。**

**新版脚本已修复**：健康检查会先用 `docker compose config --services` 取编排里实际存在的服务，只检查实际存在的 `mysql`/`redis`/`backend`/`frontend`。确认服务器上是新版：

```bash
grep -c "HEALTH_SERVICES" docker/deploy.sh   # 输出 1 或以上 = 已是新版
```

若维护的是更早的脚本，可手动改成动态获取：

```bash
SERVICES=$(docker compose -f "${COMPOSE_FILE}" --env-file "docker/prod.env" config --services | grep -vE 'deps')
for SERVICE in ${SERVICES}; do
    ...
```

### E2. 数据库备份静默跳过 → 以为有备份，其实没有

`[2/9] 备份` 里判断的是：

```bash
if docker ps --format '{{.Names}}' | grep -q '^jiaopei-prod-mysql$'; then
```

服务删掉后这个容器永远不存在，脚本只打印一句 `MySQL 容器未运行,跳过本次逻辑备份` 就继续——**看起来部署成功了，但一个备份都没做**。

修法（二选一）：

- 改用外部容器名备份：

  ```bash
  docker exec <mysql容器名> sh -c \
    'exec mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" --single-transaction --routines --triggers --events --databases jiaopei_platform' \
    | gzip -f > "${DB_BACKUP_DIR}/${TIMESTAMP}.sql.gz"
  ```

- 或直接在 1Panel 面板里给这两个库配置定时备份，`deploy.sh` 里明确注明「备份由 1Panel 负责」，避免两套备份互相以为对方在管。

### E3. 文档里失效的段落

`生产部署说明.md` 的「1C1G 低配机建议」是按 `up -d mysql redis` 串行启动写的，复用外部中间件后这段不再适用，阅读时忽略即可（文档更新跟进中）。

## 场景 F：文件上传失败 / MinIO 未就绪

### 现象

- 后端启动日志出现 `无法连接对象存储或无法创建桶 jiaopei-files，请检查 MINIO_ENDPOINT / 凭据配置`，容器反复重启；
- 或后端正常启动，但上传接口返回 500「文件写入对象存储失败，请稍后重试」；
- 文件管理页/业务页图片全部裂开（`GET /api/system/files/{id}/content` 返回 404 或 403）。

### 根因

- `deploy.sh` 执行 `up -d` 时 backend 依赖 `minio` 的 healthy 状态，MinIO 没起来 backend 就不会启动；
- `MINIO_ACCESS_KEY/MINIO_SECRET_KEY`（应用侧）与 `MINIO_ROOT_USER/MINIO_ROOT_PASSWORD`（服务端）不一致；
- 在宿主机直接 `mvn spring-boot:run` 调试，但 `cornerstone.file.provider` 被设成 `minio`、`MINIO_ENDPOINT` 还指着容器名 `minio:9000`（宿主机解析不到）；
- 403 是租户隔离：fileId 属于另一个机构，或者当前账号没有机构归属。

### 判断

```bash
cd /mnt/software/jiaopei
docker compose -f docker/docker-compose.prod.yml --env-file docker/prod.env ps minio backend
docker compose -f docker/docker-compose.prod.yml --env-file docker/prod.env logs --tail=50 minio
# 容器网络内 MinIO 是否真的活着
docker compose -f docker/docker-compose.prod.yml --env-file docker/prod.env \
  exec backend wget -qO- http://minio:9000/minio/health/live
```

### 修复

- 先单独起 MinIO：`docker compose ... up -d minio`，等 `ps minio` 显示 `healthy` 再 `up -d backend`；
- 核对 `prod.env` 里四组凭据两两一致（应用侧默认复用服务端凭据）；
- 生产 `MINIO_BIND` 保持 `127.0.0.1`，浏览器不需要直达 9000/9001；上传下载都由 backend 中转；
- 本机无 MinIO 时保持默认 `FILE_STORAGE_PROVIDER=local`，文件落在 `./data/files`（启动日志会打 WARN）。

### 验证

```bash
# 上传（token 从 POST /api/auth/login 获取）
curl -F "file=@a.png" -H "Authorization: Bearer <token>" http://<host>:5757/api/system/files
# 用返回的 fileId 取内容，应与原文件字节一致
curl -H "Authorization: Bearer <token>" http://<host>:5757/api/system/files/<fileId>/content -o out.png
# 删除后再取应为 404（未绑定业务时才允许删除）
curl -X DELETE -H "Authorization: Bearer <token>" http://<host>:5757/api/system/files/<fileId>
# 桶内对象（服务端镜像自带 mc，健康检查用的就是它）
docker exec jiaopei-prod-minio mc ls --recursive local/jiaopei-files
```

### 回滚

- 只回退文件能力：保持 MinIO 数据卷不动，回退 backend 镜像即可；`sys_file` 与桶内对象都保留，旧版本不读它们。
- 完全卸载 MinIO：先停 backend，再 `docker compose stop minio`；**不要 `down -v`**，那会把 MySQL/Redis 卷一起删掉。

## 部署前 30 秒自检

每次部署前跑一遍，能提前挡掉上面 80% 的问题：

```bash
cd /mnt/software/jiaopei
echo "--- compose 语法 ---"
docker compose -f docker/docker-compose.prod.yml --env-file docker/prod.env config > /dev/null && echo OK
echo "--- 端口占用（复用外部中间件时不应出现本项目容器）---"
sudo ss -tlnp | grep -E ':(3306|6379|80)\b' || true
echo "--- 外部中间件可达 ---"
docker run --rm --network 1panel-network alpine getent hosts <mysql容器名> <redis容器名> || true
echo "--- 磁盘 ---"
df -h /var/lib/docker | tail -1
```

## 方法论（故障复盘沉淀）

- **看第一个错，不是最后一串错。** 连锁失败时根因永远在最上面。
- **理解报错的语义。** `pathspec did not match` = git 不认识这个路径；`port already allocated` = 宿主机端口被抢；`host not found in upstream` = DNS/网络不通；`condition not reached` = 上游挂了。三类问题，三种修法，别混着猜。
- **改配置前先验证目标环境。** 库在不在、账号有没有权限、密码匹不匹配——五分钟能验证的事，能省一小时来回试错。
- **容器网络是显式声明制。** 写了 `networks:` 就脱离默认网络；跨网络访问靠「同时挂多个网络」。
- **删服务要删干净。** 服务定义、`depends_on`、环境变量里的主机名、以及部署脚本里的健康检查与备份，引用链上每一环都要清。
- **动手前备份，改完即验证。** 备份 → `compose config` 校验 → 启动 → 健康检查，四步走，随时可回滚。
