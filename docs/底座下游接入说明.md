# 底座下游接入说明

面向"用 Cornerstone 底座起一个新项目"的人。以第一个真实下游仓库（`self/achievement`，成就分发）的实测过程为准，不是设计愿景。

> 阅读前提：底座**尚未**达到"可宣布复用"（判定标准见最后一节，achievement 端到端已跑通，正式验收还差阶段五-4）。
> 当前状态：Java 侧（鉴权/系统管理/审计/模块装配）拿一个 jar 就能跑，`sys_*` 建表与最小种子也随
> `cornerstone-core` jar 自带（阶段五-0e，`classpath:cornerstone/migration` + `classpath:cornerstone/audit-migration`），
> 下游只依赖私服产物即可从零建库并登录（实测见第 8 节）。剩余缺口见第 6 节与 `achievement/docs/底座接入问题记录.md`。

## 1. 发布形态：私服上传（Nexus + Verdaccio）

| 项 | 值 |
| --- | --- |
| 后端坐标 | `com.cornerstone:cornerstone-core:0.1.1-SNAPSHOT`（开发期号） |
| Maven 私服 | Nexus 3 `http://46.38.240.16:8081` — `maven-snapshots` / `maven-releases` 两个 hosted 库，`maven-public` 组同时含这两个与 central 代理，**下游解析只写 maven-public 一个地址就够** |
| 前端私服 | Verdaccio `http://46.38.240.16:40087/` — 包 `@cornerstone/core`，当前 `0.1.1-SNAPSHOT.5`，dist-tag `snapshot`（`latest` 也指它）。**npm 没有 SNAPSHOT 语义**：同号不能覆盖，上游每次重发递增迭代号（`.2`、`.3`…），下游**装到哪个号写死哪个号** |
| 发布动作 | 后端 `cd backend && mvn deploy`（**带测试**，别加 `-DskipTests`）；前端先改 `packages/core/package.json` 的 `version`（迭代号 +1）再 `cd frontend/packages/core && npm publish --tag snapshot` |
| 实际上传物 | 只有 `jiaopei-platform-backend-parent`（pom）与 `cornerstone-core`（jar+pom）。三个下游模块在各自 pom 里 `maven.deploy.skip=true` |
| 凭据放哪 | 上传：Maven 安装级 `conf/settings.xml` 的 `<servers>`（id 对上 `distributionManagement`）、`~/.npmrc` 的 `//46.38.240.16:40087/:_auth`。**都不进 pom、不进仓库**。读取：两个私服都匿名放行，下游不用配任何密码 |
| 本机 localRepository | `D:\environment\maven\Maven-resource`（由同一份 `conf/settings.xml` 指定，**不是** `~/.m2/repository`，查产物别看错目录） |

下游解析要在自己仓库里显式声明那个 `maven-public` 仓库（`<repositories>`，快照 `updatePolicy=always`），不要只依赖构建机的全局 settings —— 换机器就断。achievement 的 `backend/pom.xml` 是模板。

**parent pom 必须一起发**：core 的 pom 里 mybatis-plus / springdoc / jjwt 均不写版本，靠 `jiaopei-platform-backend-parent` 的 `dependencyManagement` 解析。parent 上私服后，Maven 会自己去私服取它，下游不再要求本机先 `install` 过教培仓库。

升级底座只改下游一处：`backend/pom.xml` 的 `<cornerstone.version>`。

**不引入源码**：下游不要 copy `cornerstone-core` 目录、不要建同名子模块。那等于放弃验证。

## 2. 启动类契约（一处必须照抄，会静默失效）

```java
package com.<你的项目>;

@SpringBootApplication(scanBasePackages = {
    "com.cornerstone.core.auth",
    "com.cornerstone.core.system",
    "com.cornerstone.core.tenant",
    "com.cornerstone.core.audit",
    "com.cornerstone.core.common",
    "com.cornerstone.core.config",
    "com.cornerstone.core.file"
})
@ConfigurationPropertiesScan("com.<你的项目>")   // 只登记本项目自己的配置类
public class XxxApplication { ... }
```

1. `scanBasePackages` 只列底座七个顶层包（`file` 是通用文件能力，漏扫会让上传/下载接口静默 404）。**不要放宽到 `com.cornerstone`**——那会把 classpath 上所有业务 `@Component` 无条件扫进来，模块开关形同虚设。
2. ~~`@ConfigurationPropertiesScan` 的底座包必须显式列出~~ **已收口（0.1.1-SNAPSHOT 起）**。底座自己带 `com.cornerstone.core.config.CornerstonePropertiesConfiguration`（`@EnableConfigurationProperties(CornerstoneProperties.class)`），它落在必扫的七个顶层包之一，所以下游只写本项目包根就行。这条以前是真坑：主类包根与底座不同时，默认扫描取不到 `CornerstoneProperties`，`cornerstone.*` 全取默认值且**启动不报错**（公共路径配了仍 401、开关关了仍装配）。守护：`ModuleSwitchGuardTest#coreMustSelfRegisterItsConfigurationProperties`（底座侧断言每个 `@ConfigurationProperties` 都被登记，下游侧断言不再扫底座 properties 包）。写在 `@Configuration` 而不是自动配置类上是有意的——底座的 `DataSource`/`SqlSessionFactory` 必须早于 Boot 与 MyBatis-Plus 的自动配置出现。下游若仍保留 `@ConfigurationPropertiesScan("com.cornerstone.core.config.properties")` 不会出错（同名 bean 去重），但那行已经没有作用，建议删掉。
3. 底座新增顶层包时，本仓库会同步改主类；下游要跟着补这一行（当前无通知机制，属已知缺陷）。

## 3. 业务模块怎么装

在模块 jar 里放 `src/main/resources/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`，内容是实现类全名：

```
com.<你的项目>.module.<模块>.config.<Xxx>ModuleAutoConfiguration
```

配置类形态照抄 `module-organization` 的 `OrganizationModuleAutoConfiguration`：`@AutoConfiguration` + `@ConditionalOnProperty(prefix = "cornerstone.modules.enabled", name = "<模块码>", havingValue = "true", matchIfMissing = true)` + `@ComponentScan(basePackages = 本模块包根, excludeFilters = AutoConfigurationExcludeFilter)` + `@MapperScan(basePackages = 本模块 mapper 包, sqlSessionFactoryRef = MybatisPlusConfig.PRIMARY_FACTORY, sqlSessionTemplateRef = MybatisPlusConfig.PRIMARY_SESSION)`。

再加一个 `ModuleDescriptor` 实现（`code()` 必须等于开关里的模块码），`/api/system/bootstrap` 与 OpenAPI 描述会自动列出它，不用改底座任何消费代码。

**加/减模块只改 `app/pom.xml` 的依赖 + yml 的开关条目**，不动启动类。

## 4. 配置清单

`cornerstone.*` 全部键（超出这些的底座配置不存在，别猜）：

```yaml
cornerstone:
  security:
    data-key: ${DATA_ENCRYPT_KEY}        # 敏感字段 AES 密钥（SHA-256 派生），生产必填且不可更换
    public-paths:                        # 免鉴权路径，Ant 风格
      - /api/health
      - /api/system/bootstrap
      - /api/auth/**
      - /v3/api-docs/**
      - /swagger-ui/**
      - /swagger-ui.html
  modules:
    enabled:                             # 模块码 -> 开关；未配置视为开启
      <模块码>: ${MODULE_<X>_ENABLED:true}
  flyway:
    locations:                             # 业务库迁移目录（本项目脚本在前，底座基线在后）
      - classpath:db/migration             # 自己的业务表，号段 V200+
      - classpath:cornerstone/migration    # 底座基线 V100~V199，来自 core jar，全新项目必配
    audit-locations:                       # 日志库迁移目录，同上；没有自建日志表时只留底座这一条
      - classpath:cornerstone/audit-migration
  audit-db:
    host: 127.0.0.1
    port: 3306
    database: cornerstone_log            # 默认值，各部署方覆盖
    username: root
    password: ""
  auth:
    jwt:
      secret: ${AUTH_JWT_SECRET}         # HS256，≥32 字节，生产必须覆盖

spring:
  flyway:
    enabled: false                       # 必须 false：迁移由底座两个 Flyway bean 自管
  data.redis.database: <每个项目不同>     # 见第 7 节
mybatis-plus:
  type-aliases-package: com.cornerstone,com.<你的项目>   # 两个包根都要列
```

两个目录配置项都是 `List<String>`，写成 YAML 列表或逗号分隔单行都可以。**它们必须是 `@ConfigurationProperties`，不能退回 `@Value`**：YAML 列表在 Environment 里是 `locations[0]`/`locations[1]` 两个键，`@Value("${...}")` 取不到列表、会**静默回落到默认值**（`classpath:db/migration` / `classpath:db/audit-migration`），症状是"配置写了、日志却 `No migrations found`，且启动不报错"。教培自己的配置值恰好等于默认值，所以这个坑在本仓库不可见，第一次撞到是下游配第二条目录时。守护测试：`CornerstoneBaselineGuardTest#flywayLocationsMustBindTheYamlListForm`。

配了 `classpath:cornerstone/migration` 之后，全新项目不用再自带 `sys_*` 建表脚本；审计表同理走 `classpath:cornerstone/audit-migration`。目录缺失（比如某个模块开关关了、jar 不在 classpath）Flyway 只告警不失败。

**已经跑过 V100/V101 的老库升级底座 = 照常换 jar 重启**，底座后续以 `V102`、`V103`… 追加修正脚本（例：`V102__neutralize_role_form_hints.sql` 把角色表单占位语里的教培名词换成中性说法）。**基线脚本一旦在某个环境执行过就不再原地改**（回改会撞 checksum，下游重启直接 validate 失败），所以种子文案的修正是新增脚本，不是把 V101 里的字改掉。

## 5. 命名边界（决定新东西叫什么、放哪）

| 归属 | 口径 |
| --- | --- |
| 底座身份 | `cornerstone`：Java 包根 `com.cornerstone.core.*`、配置前缀 `cornerstone.*`、Redis key 前缀 `cornerstone:`、浏览器 storage key `cornerstone.*`、Hikari 池名 |
| 你的项目身份 | 库名、镜像/容器名、`spring.application.name`、业务表前缀、Maven groupId 与 Java 包根 |
| 底座表 | 一律 `sys_` 前缀（`sys_user_account` / `sys_role` / `sys_user_role_rel` / `sys_institution` / `sys_menu` / `sys_role_menu` / `sys_dict_*` / `sys_list_config` / `sys_data_source` / `sys_system_config`）。**例外**：审计表叫 `oper_log`，0b 改名时漏了它，与"底座表统一 `sys_`"的口径不一致，见第 6 节 8 |
| 业务表 | 自定义前缀（本仓库用 `jp_`，achievement 用 `ac_`），不要复用 `sys_` |
| 权限码 | 底座机构（=租户）接口用 `tenant:*`，底座系统管理用 `system:*`；业务模块用自己域名（`<模块>:read` / `<模块>:write`）。**不要给底座接口挂业务前缀的码** |
| 环境变量 | 中性、不带前缀：`AUTH_JWT_SECRET`、`DATA_ENCRYPT_KEY`、`DB_*`、`REDIS_*`、`MODULE_*_ENABLED` |

Redis key 不是表：会话布局为 `cornerstone:token:{jwt}`（序列化 `AuthenticatedUser`，TTL 取系统参数 `auth.token.expire_hours`）与 `cornerstone:user:tokens:{userId}`（强制下线用）。

## 6. 现在还不干净的地方（接入前必读）

1. ~~**底座基线迁移不在 core jar 里**~~ **已收口（阶段五-0e，2026-09-21）**。底座 11 张 `sys_*` 表结构 + 69 行最小种子随 `cornerstone-core` jar 发布，目录 `classpath:cornerstone/migration`（`V100__cornerstone_core_schema.sql` / `V101__cornerstone_core_seed.sql`），审计表在 `classpath:cornerstone/audit-migration`（`V100__cornerstone_oper_log.sql`）。下游只要把这两个目录写进 `cornerstone.flyway.locations` / `audit-locations` 就能从空库建到可登录，不再需要抄本——achievement 已按此切换（它的手工抄本移进 `db/attic/`）。**教培自己不配这两个目录**：它的 `sys_` 表是 V7/V8/…/V45 长出来的，两套目录同时启用会重复建表、Flyway 直接启动失败。两条路径的最终形态一致，实测口径见第 8 节；防漂移由 `CornerstoneBaselineGuardTest`（8 项静态守护）拦着。种子口径：只 id=1 的测试机构 + admin、菜单只留底座段、角色权限串只有底座码、不种 `auth.login.page_tip`、`admin` 起始口令 `{noop}Cornerstone@123456` 且 `force_change_password=1`（**jar 里的口令属公开信息，强制改密不是可选项**）。
2. 版本号分段：底座基线占 `V100~V199`（core jar 的 `classpath:cornerstone/migration`、`classpath:cornerstone/audit-migration`），新项目的业务脚本从 `V200` 起，`V1~V99` 不使用（那是教培长链的历史区间，把业务脚本放这里会排在底座建表之前）。**Flyway 不允许跨 location 重版本号**，否则启动即失败。
3. ~~`oper_log` 建表脚本要下游自带副本~~ **已随 0e 收口**：审计建表脚本也进 core jar 了。漂移后果仍是静默的（审计写库异常被切面吞掉，只丢日志），所以配了 `audit-locations` 后要主动打一次登录/写操作接口，再查 `/api/system/operlogs` 确认真的落进去了。
4. core jar 传递依赖版本来自本仓库 parent pom —— **parent pom 已随 `mvn deploy` 一起上私服**，下游不再要求本机先 install 过教培仓库（实测：把本机 `Maven-resource/com/cornerstone` 整个挪开后，achievement 仍能从 `maven-public` 取到 parent 与 core 并编译通过）。对外发布（跨公司/给不可信方）前仍应用 `flatten-maven-plugin` 把版本写平，省掉"多发布一个 pom"这条隐式契约。
5. ~~`ExternalIdParser.FIELD_NAME_ZH` 里仍是教培词表（校区/班级/学员…）~~ **已收口（0.1.1-SNAPSHOT 起）**。底座只留自己那三个概念（机构/角色/菜单 ID），业务字段的中文名改由模块登记：实现底座的 `ExternalIdFieldLabelContributor`（返回 `Map<字段名, 中文名>`）并放成自己模块 `config` 包里的 `@Component`，`ExternalIdLabelRegistry` 启动时汇聚，模块没装就用原始字段名报错。键会先归一化（小写、去下划线），所以写字段名的驼峰形式即可；**同名 key 底座优先**，业务方覆盖不了底座的三个概念。参考实现：`module-organization` 的 `OrganizationExternalIdLabels`、`module-education` 的 `EducationExternalIdLabels`。守护是产物级的：`ExternalIdVocabularyGuardTest` 会扫 core 每个 class 的字节码常量池与 jar 内基线 SQL，`@Schema` example、异常文案里漏一个"校区"都会失败。
6. 前端 `@cornerstone/core` 已发到 Verdaccio，但是**源码形态**：包里只有 `src`（53 个文件、106 kB），`exports` 用 `"./*": "./src/*"` 把深路径直映射到源文件，没有 `dist`、没有 `.d.ts`。代价是消费方要自己编译我们的源码：vite 需 `optimizeDeps.exclude: ['@cornerstone/core']`（否则预打包按已编译依赖处理，`.vue` 进不去），`vue-tsc` 会连带检查包内源码（我们的类型问题会在下游报错）。**下游接入这条链已在 achievement 实测跑通**（登录、系统管理页、业务模块包注入导航，见第 8 节），剩下的欠账只有一项：**真实构建产物（`vite build --lib` + `.d.ts`）**。
   - **依赖已改成 `peerDependencies`**（`0.1.1-SNAPSHOT.2` 起）：原本写在 `dependencies` 里，pnpm 会在 `node_modules/.pnpm` 长出第二份 vue/element-plus，两个 vue 实例直接打散 pinia 与依赖注入。现在宿主（壳工程）自己声明这些依赖，包只声明 peer 范围。

   - **当天发当天装会被 pnpm 11 拦**：`minimumReleaseAge` 默认 1 天，且 `minimumReleaseAgeExclude` 只在解析阶段生效、验证阶段仍拒。下游在自己 `pnpm-workspace.yaml` 里 `minimumReleaseAge: 0`，防护换成 pin 精确版本。

8. 审计表名 `oper_log` 没跟上"底座表统一 `sys_` 前缀"的口径（0b 只改了 4 张认证/机构类表）。下游若自建日志表容易撞名或按 `sys_` 预期找不到表。改名要走新增迁移，不能回改 V1。
9. ~~**11 张底座表的 12 个唯一键全部不含 `deleted`**~~ **已收口（阶段五-0e，教培侧 V45 + core 基线 V100 同步）**。软删表的唯一键原本只有业务列，"删了再建同名"会在服务层 `selectCount`（被 `@TableLogic` 限死只数 `deleted=0`）放行、到数据库才撞键，症状是 500 而不是校验提示。现在 `uk(code, deleted)` 两侧一致，守护测试 `everyBaselineUniqueKeyMustIncludeDeleted` 拦回归。**残留边界要知道**：`deleted` 是 0/1 而非时间戳，同一业务值**最多只能留一条软删记录**，第二条软删同名记录仍撞键——这是治标，彻底解要改物理删除或把 `deleted` 换成 `deleted_at`，另议。你自己的业务表按同样口径建（`uk(<业务列>, deleted)`）。
10. ~~`sys_system_config` 表尾是 `utf8mb4_0900_ai_ci`~~ **已收口（V44，2026-09-21）**。根因不是"某次 `MODIFY` 手滑"，而是 V14 建表只写了 `DEFAULT CHARSET=utf8mb4`、**没写 `COLLATE`**，排序规则于是随服务器默认走（MySQL 8.4 默认 `utf8mb4_0900_ai_ci`）——同一脚本在不同环境长出不同表。V44 用 `CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci` 把教培库归一，全新库回放也收敛（V14 建成 0900 → V44 改回 unicode_ci，scratch 库实测）。**给下游的口径：本项目只支持 MySQL 8.x，不再兼容 5.x；但排序规则统一 `utf8mb4_unicode_ci`，建表必须把 `COLLATE` 写死，别依赖服务器默认。** 0e 的 core 基线脚本按这条写。
11. ~~**授权变更后不失效会话（底座缺陷，achievement 实测复现，未修）**。~~ **已回灌（`cornerstone-core:0.1.1-20260921.135504-5`，2026-09-21）**。`invalidateUserSessions` 只在"禁用/注销用户"两处被调用；`SystemRoleServiceImpl.updateRole`、`SystemUserServiceImpl.updateRoles`、`SystemMenuServiceImpl.updateRoleMenus` 三条改授权的路径**都没调**。实测：给角色加一个权限码后，当前会话仍 200、`/api/auth/me` 返回的还是旧的 11 项。反向同理——**收回权限要等 token 自然过期（默认 12 小时）**。本仓库 AGENTS.md「权限回收即时生效」那条约定在底座里根本没实现，第一个项目没撞过是因为改完刷新页面看起来"生效了"。下游在自己业务里补调也补不干净（拿不到"哪些用户持有这个角色"的反查，那属底座数据）。**修法已落地**：`AuthApplicationService` 新增 `invalidateUserSessionsByRole(roleId)`（在 `AuthApplicationServiceImpl` 里按 `sys_user_role_rel` 反查持有用户、去重后逐个清 Redis 会话），三条路径各自补调：`SystemRoleServiceImpl.updateRole`、`SystemMenuServiceImpl.updateRoleMenus` 用 byRole 版，`SystemUserServiceImpl.updateRoles` 用 userId 版。守护：`SystemRoleServiceImplTest`、`AuthApplicationServiceImplTest` 的两条 byRole 用例、`SystemMenuServiceImplTest` 与 `SystemUserServiceImplTest` 的 verify。运行期实测两仓库都过（见 §8）。

   - **仍未覆盖的同类路径（新条目 15）**：改菜单节点自身的 `permissionCode`（`updateMenu`/`deleteMenu`）不失效会话——那是"哪些角色挂了这张菜单 → 哪些用户持有角色"的两跳反查，本轮没做。

14. **私服自身的暴露面（接入方要知道，属基建不属代码）**：两台都在公网 IP 上。Verdaccio 开着**自助注册**（本机 `~/.npmrc` 里那个发布账号就是这么建出来的），意味着任何人都能注册后往同一个 scope 里 publish `@cornerstone/core` 的更高版本，下游只要写 `^0.1.1` 就可能被静默升级成投毒包。Nexus 侧匿名 deploy 实测被拒（401，正确），匿名读放行（下游免凭据，符合预期），但上传用的是 **admin 超管账号**。> **2026-09-21 用户决定：现阶段目标是把分发流程打通，加固（关自助注册 / 换 deploy 专用账号）暂不做，后续再研究。** 唯一仍然生效的软件侧约束：**消费方一律 pin 精确版本，不要写 `^`**。

## 7. 同机并行的资源隔离（实测约定）

| | jiaopei-platform | achievement |
| --- | --- | --- |
| 后端 / 前端端口 | 8080 / 5173 | 18081 / 5174（2026-09-21 由 8081 上调：服务器 8081 是 Nexus。下文实测记录里的 8081 是当时的实况，不回改） |
| MySQL 库 | `jiaopei_platform` / `jiaopei_log` | `achievement_platform` / `achievement_log` |
| Redis | db 0 | db 1 |
| dev JWT / data-key 默认值 | 各自不同 | 各自不同 |

**Redis 必须分库**：会话 key 里的 `userId` 是各库自增/雪花，跨项目会撞号；共用 db 0 时 A 项目改密调 `invalidateUserSessions(userId)` 会把 B 项目同 ID 用户踢下线。JWT 密钥也要不同，否则一个项目的合法 token 在另一个项目能验签通过。
