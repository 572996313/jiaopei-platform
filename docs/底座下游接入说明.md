# 底座下游接入说明

面向"用 Cornerstone 底座起一个新项目"的人。以第一个真实下游仓库（`self/achievement`，成就分发）的实测过程为准，不是设计愿景。

> 阅读前提：底座**尚未**达到"可宣布复用"。当前状态是"骨架可复用、基线数据不可复用"——
> Java 侧（鉴权/系统管理/审计/模块装配）拿一个 jar 就能跑，`sys_*` 建表脚本还留在本仓库，
> 新项目起得来但登录不了（achievement 靠一份手工裁剪的基线抄本先跑通了登录，那是下游自解，不改底座事实）。
> 缺口见第 6 节与 `achievement/docs/底座接入问题记录.md`。

## 1. 发布形态：私服上传（Nexus + Verdaccio）

| 项 | 值 |
| --- | --- |
| 后端坐标 | `com.cornerstone:cornerstone-core:0.1.1-SNAPSHOT`（开发期号） |
| Maven 私服 | Nexus 3 `http://46.38.240.16:8081` — `maven-snapshots` / `maven-releases` 两个 hosted 库，`maven-public` 组同时含这两个与 central 代理，**下游解析只写 maven-public 一个地址就够** |
| 前端私服 | Verdaccio `http://46.38.240.16:40087/` — 包 `@cornerstone/core@0.1.1-SNAPSHOT`，dist-tag `snapshot`（当前 `latest` 也指向它，因为还没有别的版本） |
| 发布动作 | 后端 `cd backend && mvn deploy`（**带测试**，别加 `-DskipTests`）；前端 `cd frontend/packages/core && npm publish --tag snapshot` |
| 实际上传物 | 只有 `jiaopei-platform-backend-parent`（pom）与 `cornerstone-core`（jar+pom）。三个下游模块在各自 pom 里 `maven.deploy.skip=true` |
| 凭据放哪 | 上传：Maven 安装级 `conf/settings.xml` 的 `<servers>`（id 对上 `distributionManagement`）、`~/.npmrc` 的 `//46.38.240.16:40087/:_auth`。**都不进 pom、不进仓库**。读取：两个私服都匿名放行，下游不用配任何密码 |
| 本机 localRepository | `D:\environment\maven\Maven-resource`（由同一份 `conf/settings.xml` 指定，**不是** `~/.m2/repository`，查产物别看错目录） |

下游解析要在自己仓库里显式声明那个 `maven-public` 仓库（`<repositories>`，快照 `updatePolicy=always`），不要只依赖构建机的全局 settings —— 换机器就断。achievement 的 `backend/pom.xml` 是模板。

**parent pom 必须一起发**：core 的 pom 里 mybatis-plus / springdoc / jjwt 均不写版本，靠 `jiaopei-platform-backend-parent` 的 `dependencyManagement` 解析。parent 上私服后，Maven 会自己去私服取它，下游不再要求本机先 `install` 过教培仓库。

升级底座只改下游一处：`backend/pom.xml` 的 `<cornerstone.version>`。

**不引入源码**：下游不要 copy `cornerstone-core` 目录、不要建同名子模块。那等于放弃验证。

## 2. 启动类契约（两处必须照抄，且都会静默失效）

```java
package com.<你的项目>;

@SpringBootApplication(scanBasePackages = {
    "com.cornerstone.core.auth",
    "com.cornerstone.core.system",
    "com.cornerstone.core.tenant",
    "com.cornerstone.core.audit",
    "com.cornerstone.core.common",
    "com.cornerstone.core.config"
})
@ConfigurationPropertiesScan({
    "com.cornerstone.core.config.properties",   // 必须显式写：默认只扫主类所在包
    "com.<你的项目>"
})
public class XxxApplication { ... }
```

1. `scanBasePackages` 只列底座六个顶层包。**不要放宽到 `com.cornerstone`**——那会把 classpath 上所有业务 `@Component` 无条件扫进来，模块开关形同虚设。
2. `@ConfigurationPropertiesScan` 的底座包**必须显式列出**。主类包根与底座不同时，默认扫描取不到 `CornerstoneProperties`，症状是 `cornerstone.*` 全取默认值而**启动不报错**（公共路径配了仍 401、开关关了仍装配）。实测踩点，建议照 `achievement/backend/app/src/test/java/.../ModuleSwitchGuardTest.java` 加一条守护测试。
3. 底座新增顶层包时，本仓库会同步改主类；下游要跟着补这一行（当前无通知机制，属已知缺陷）。

## 3. 业务模块怎么装

在模块 jar 里放 `src/main/resources/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`，内容是实现类全名：

```
com.<你的项目>.module.<模块>.config.<Xxx>ModuleAutoConfiguration
```

配置类形态照抄 `module-organization` 的 `OrganizationModuleAutoConfiguration`：`@AutoConfiguration` + `@ConditionalOnProperty(prefix = "cornerstone.modules.enabled", name = "<模块码>", havingValue = "true", matchIfMissing = true)` + `@ComponentScan(basePackages = 本模块包根, excludeFilters = AutoConfigurationExcludeFilter)` + `@MapperScan(basePackages = 本模块 mapper 包, sqlSessionFactoryRef = MybatisPlusConfig.PRIMARY_FACTORY, sqlSessionTemplateRef = MybatisPlusConfig.PRIMARY_SESSION)`。

再加一个 `ModuleDescriptor` 实现（`code()` 必须等于开关里的模块码），`/api/system/bootstrap` 与 OpenAPI 描述会自动列出它，不用改底座任何消费代码。

**加/减模块只改 `app/pom.xml` 的依赖 + yml 的开关条目**，不动启动类。

## 4. 配置清单

`cornerstone.*` 全部键（超出这些的底座配置不存在，别猜）：

```yaml
cornerstone:
  security:
    data-key: ${DATA_ENCRYPT_KEY}        # 敏感字段 AES 密钥（SHA-256 派生），生产必填且不可更换
    public-paths:                        # 免鉴权路径，Ant 风格
      - /api/health
      - /api/system/bootstrap
      - /api/auth/**
      - /v3/api-docs/**
      - /swagger-ui/**
      - /swagger-ui.html
  modules:
    enabled:                             # 模块码 -> 开关；未配置视为开启
      <模块码>: ${MODULE_<X>_ENABLED:true}
  flyway:
    locations:
      - classpath:db/migration           # 业务库迁移目录，模块要自带脚本时在此追加
  audit-db:
    host: 127.0.0.1
    port: 3306
    database: cornerstone_log            # 默认值，各部署方覆盖
    username: root
    password: ""
  auth:
    jwt:
      secret: ${AUTH_JWT_SECRET}         # HS256，≥32 字节，生产必须覆盖

spring:
  flyway:
    enabled: false                       # 必须 false：迁移由底座两个 Flyway bean 自管
  data.redis.database: <每个项目不同>     # 见第 7 节
mybatis-plus:
  type-aliases-package: com.cornerstone,com.<你的项目>   # 两个包根都要列
```

日志库（`oper_log`）与业务库分两个数据源、两个 Flyway：业务库走 `cornerstone.flyway.locations`，日志库走**硬编码**的 `classpath:db/audit-migration`——该目录目前不在 core jar 里，**下游要自带一份 `V1__create_oper_log_table.sql`**（见第 6 节缺口）。

## 5. 命名边界（决定新东西叫什么、放哪）

| 归属 | 口径 |
| --- | --- |
| 底座身份 | `cornerstone`：Java 包根 `com.cornerstone.core.*`、配置前缀 `cornerstone.*`、Redis key 前缀 `cornerstone:`、浏览器 storage key `cornerstone.*`、Hikari 池名 |
| 你的项目身份 | 库名、镜像/容器名、`spring.application.name`、业务表前缀、Maven groupId 与 Java 包根 |
| 底座表 | 一律 `sys_` 前缀（`sys_user_account` / `sys_role` / `sys_user_role_rel` / `sys_institution` / `sys_menu` / `sys_role_menu` / `sys_dict_*` / `sys_list_config` / `sys_data_source` / `sys_system_config`）。**例外**：审计表叫 `oper_log`，0b 改名时漏了它，与"底座表统一 `sys_`"的口径不一致，见第 6 节 8 |
| 业务表 | 自定义前缀（本仓库用 `jp_`，achievement 用 `ac_`），不要复用 `sys_` |
| 权限码 | 底座机构（=租户）接口用 `tenant:*`，底座系统管理用 `system:*`；业务模块用自己域名（`<模块>:read` / `<模块>:write`）。**不要给底座接口挂业务前缀的码** |
| 环境变量 | 中性、不带前缀：`AUTH_JWT_SECRET`、`DATA_ENCRYPT_KEY`、`DB_*`、`REDIS_*`、`MODULE_*_ENABLED` |

Redis key 不是表：会话布局为 `cornerstone:token:{jwt}`（序列化 `AuthenticatedUser`，TTL 取系统参数 `auth.token.expire_hours`）与 `cornerstone:user:tokens:{userId}`（强制下线用）。

## 6. 现在还不干净的地方（接入前必读）

1. **底座基线迁移不在 core jar 里**。`sys_*` 建表 + 种子在本仓库 `backend/app/src/main/resources/db/migration/V1..V44`，与 `jp_*` 业务表混在同一条版本链上。新项目因此**能启动、不能登录**（`/api/auth/login-page` 500：`Table 'xxx_platform.sys_system_config' doesn't exist`）。这是 0e 的交付内容，做完之前别宣布底座可复用。achievement 目前用一份**手工裁剪抄本**（它的 `V100__cornerstone_baseline.sql`）临时解掉，抄本口径：11 张表结构 + 69 行底座最小种子，只留 id=1 的测试机构/admin、菜单只留底座段、角色权限串裁掉业务码、不种 `auth.login.page_tip`、口令换 `{noop}` 起始口令、表尾 collation 归一 `utf8mb4_unicode_ci`。**下游解的是自己的燃眉之急，不是底座变干净了** —— 0e 落地后这份抄本要删掉换成 core 自带脚本。
2. 版本号分段：0e 之后底座基线占 `V100~V199`（core jar 内 `classpath:db/migration/core`），新项目的业务脚本从 `V200` 起，`V1~V99` 不使用（那是教培长链的历史区间，把业务脚本放这里会排在底座建表之前）。**Flyway 不允许跨 location 重版本号**，否则启动即失败。
3. `oper_log` 建表脚本要下游自带副本 → 与底座实体字段必然漂移（漂移后果静默：审计写库异常被切面吞掉，只丢日志）。同样等 0e。
4. core jar 传递依赖版本来自本仓库 parent pom —— **parent pom 已随 `mvn deploy` 一起上私服**，下游不再要求本机先 install 过教培仓库（实测：把本机 `Maven-resource/com/cornerstone` 整个挪开后，achievement 仍能从 `maven-public` 取到 parent 与 core 并编译通过）。对外发布（跨公司/给不可信方）前仍应用 `flatten-maven-plugin` 把版本写平，省掉"多发布一个 pom"这条隐式契约。
5. `ExternalIdParser.FIELD_NAME_ZH` 里仍是教培词表（校区/班级/学员…），下游报错消息会带出教培名词。待 SPI 化。
6. 前端 `@cornerstone/core` 已发到 Verdaccio，但是**源码形态**：包里只有 `src`（53 个文件、106 kB），`exports` 用 `"./*": "./src/*"` 把深路径直映射到源文件，没有 `dist`、没有 `.d.ts`。代价是消费方要自己编译我们的源码：vite 需 `optimizeDeps.exclude: ['@cornerstone/core']`（否则预打包按已编译依赖处理，`.vue` 进不去），`vue-tsc` 会连带检查包内源码（我们的类型问题会在下游报错）。**真实构建（`vite build --lib` + 类型产物 + peerDependencies）仍是阶段五-3 的欠账**，私服配好不等于这一步做完了。
7. 底座六个顶层包名要抄进下游启动类，上游改包结构时下游没有通知机制。彻底解法（底座也走自动配置）受"MyBatis 数据源必须早于 Boot/MP 自动配置"约束，需单独验证，**不要顺手改**。
8. 审计表名 `oper_log` 没跟上"底座表统一 `sys_` 前缀"的口径（0b 只改了 4 张认证/机构类表）。下游若自建日志表容易撞名或按 `sys_` 预期找不到表。改名要走新增迁移，不能回改 V1。
9. **11 张底座表的 12 个唯一键全部不含 `deleted`**，与「逻辑删除 + 唯一索引须含 `deleted`」相悖：软删后建同名记录，服务层 `selectCount`（被 `@TableLogic` 限死只数 `deleted=0`）会先放行、到数据库才撞键，症状是 500 而不是校验提示。下游抄基线时会原样继承这个坑，0e 收口前请先按"用户/角色/机构/菜单/字典/列表配置/数据源/参数各会被软删重建一次"来设计自己的业务表，别跟着抄。
10. ~~`sys_system_config` 表尾是 `utf8mb4_0900_ai_ci`~~ **已收口（V44，2026-09-21）**。根因不是"某次 `MODIFY` 手滑"，而是 V14 建表只写了 `DEFAULT CHARSET=utf8mb4`、**没写 `COLLATE`**，排序规则于是随服务器默认走（MySQL 8.4 默认 `utf8mb4_0900_ai_ci`）——同一脚本在不同环境长出不同表。V44 用 `CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci` 把教培库归一，全新库回放也收敛（V14 建成 0900 → V44 改回 unicode_ci，scratch 库实测）。**给下游的口径：本项目只支持 MySQL 8.x，不再兼容 5.x；但排序规则统一 `utf8mb4_unicode_ci`，建表必须把 `COLLATE` 写死，别依赖服务器默认。** 0e 的 core 基线脚本按这条写。
11. **私服自身的暴露面（接入方要知道，属基建不属代码）**：两台都在公网 IP 上。Verdaccio 开着**自助注册**（本机 `~/.npmrc` 里那个发布账号就是这么建出来的），意味着任何人都能注册后往同一个 scope 里 publish `@cornerstone/core` 的更高版本，下游只要写 `^0.1.1` 就可能被静默升级成投毒包。Nexus 侧匿名 deploy 实测被拒（401，正确），匿名读放行（下游免凭据，符合预期），但上传用的是 **admin 超管账号**。> **2026-09-21 用户决定：现阶段目标是把分发流程打通，加固（关自助注册 / 换 deploy 专用账号）暂不做，后续再研究。** 唯一仍然生效的软件侧约束：**消费方一律 pin 精确版本，不要写 `^`**。

## 7. 同机并行的资源隔离（实测约定）

| | jiaopei-platform | achievement |
| --- | --- | --- |
| 后端 / 前端端口 | 8080 / 5173 | 8081 / 5174 |
| MySQL 库 | `jiaopei_platform` / `jiaopei_log` | `achievement_platform` / `achievement_log` |
| Redis | db 0 | db 1 |
| dev JWT / data-key 默认值 | 各自不同 | 各自不同 |

**Redis 必须分库**：会话 key 里的 `userId` 是各库自增/雪花，跨项目会撞号；共用 db 0 时 A 项目改密调 `invalidateUserSessions(userId)` 会把 B 项目同 ID 用户踢下线。JWT 密钥也要不同，否则一个项目的合法 token 在另一个项目能验签通过。
