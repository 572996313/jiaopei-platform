# 本地门禁使用教程（`scripts/ci-check.sh`）

> 面向：本项目所有开发同学。看不懂 Docker / CI / YAML 也能照着用。
> 一句话：**提交前跑一条命令，看到 `全部通过 ✔` 就可以提交了。**

---

## 一、它是什么

`scripts/ci-check.sh` 是仓库自带的**本地检查脚本**。它把「提交代码前必须满足的检查」串成一条命令，一次跑完。

### 为什么需要它

本仓库的远程在 **Gitee**（`https://gitee.com/liu-xiaofei001/educational-training-gateway.git`），不是 GitHub。仓库里那份 `.github/workflows/ci.yml` 是 GitHub Actions 的配置，**Gitee 不会执行它**。也就是说：

> 你推上去的代码，**没有任何服务器帮你检查**。检查只能自己在本地做。

`scripts/ci-check.sh` 就是这件事的本地版。

### 它检查什么

| 步骤 | 检查内容 | 大概耗时 | 挡住的典型问题 |
|---|---|---|---|
| 1/4 | 后端 `mvn test` | 1~2 分钟 | 单测失败、**架构规范被破坏**、接口签名改了调用方没同步 |
| 2/4 | 前端 `eslint` | 10 秒 | 代码规范（未使用变量、`==` 代替 `===`、包边界违规等） |
| 3/4 | 前端 `vue-tsc -b && vite build` | 20~40 秒 | TypeScript 类型错误、构建失败 |
| 4/4 | 小程序 `vue-tsc --noEmit` | 10~20 秒 | 小程序端类型错误 |

热缓存下全程约 **2 分钟**；第一次跑（要下载 Maven 依赖）会久一些。

## 二、怎么用（三步）

### 第 1 步：打开 Git Bash

在项目根目录（有 `AGENTS.md`、`backend/`、`frontend/` 的那一层）右键 → **Git Bash Here**。

> 也可以用 VS Code 的终端，把默认终端切成 Git Bash，或者直接敲 `bash` 进入。

### 第 2 步：敲命令

```bash
bash scripts/ci-check.sh
```

### 第 3 步：看结果

**通过**——最后一行是：

```
全部通过 ✔
```

**不通过**——脚本会在出错那一步停下，并打印错误信息。看错误信息里提到的**文件名和行号**去改，改完重新跑。

---

## 三、只跑其中一步（省时间）

改了什么就只跑什么，不用每次都全跑。

```bash
bash scripts/ci-check.sh backend          # 只跑后端测试（改 Java 代码时用）
bash scripts/ci-check.sh frontend-lint    # 只跑前端 eslint（改前端代码时先跑这个，最快）
bash scripts/ci-check.sh frontend-build   # 只跑前端类型检查 + 构建
bash scripts/ci-check.sh miniapp          # 只跑小程序类型检查
```

**推荐节奏**：

1. 改代码过程中——改前端就频繁 `frontend-lint`，改后端就频繁 `backend`（都很快，能立刻发现问题）
2. 准备提交前——跑一次**不带参数**的完整版，确认 `全部通过 ✔`

## 四、常见报错怎么办

### 情况 1：`未找到 JDK 21`

```
未找到 JDK 21：请把 JAVA_HOME 或 JDK21_HOME 指向 JDK 21 安装目录后重试
```

**原因**：本机没装 JDK 21，或者装在脚本不认识的位置。

**解决**：找到你机器上的 JDK 21 目录，用 `JDK21_HOME` 告诉脚本：

```bash
JDK21_HOME="D:/software/jdk-21" bash scripts/ci-check.sh
```

> 脚本会自动依次找这几个位置：`JAVA_HOME` → `JDK21_HOME` → `C:/Program Files/Java/jdk-21.0.12` → `~/.posh_sdk/java/21.0.9-oracle`。第一个是 JDK 21 的就用。这套定位逻辑放在 `scripts/lib/jdk21.sh`，`restart-backend.sh` 共用同一份。

### 情况 2：后端报 `class file version 65.0`

```
... has been compiled by a more recent version of the Java Runtime (class file version 65.0),
this version of the Java Runtime only recognizes class file versions up to 52.0
```

**原因**：用 JDK 8 去跑 JDK 21 编译出来的测试类（65 = Java 21，52 = Java 8）。

**说明**：这个坑脚本已经修好了——它会自动切到 JDK 21，不会拿 JDK 8 硬跑。如果你还是看到这个报错，说明你**没走脚本**、直接敲了 `mvn test`。改成走脚本即可。

> 想直接跑 Maven 也行，但要先手动切 JDK：
> PowerShell：`$env:JAVA_HOME='C:\Program Files\Java\jdk-21.0.12'` 然后 `mvn test`
> 这个设置只对当前窗口有效，关掉就恢复。

### 情况 3：前端 `eslint` 报一堆错

先试自动修复：

```bash
cd frontend
pnpm lint:fix
```

修完还剩下的必须手工改。**不要**用 `// eslint-disable` 糊过去——除非你有明确理由。

### 情况 4：`command not found: pnpm` 或 `mvn`

- 缺 `pnpm`：`npm i -g pnpm`
- 缺 `mvn`：装 Maven，或直接用 IDEA 自带的（`D:\environment\maven\...` 之类）
- 第一次跑前端前记得先 `cd frontend && pnpm install`，小程序同理 `cd miniapp && pnpm install`

### 情况 5：后端测试报架构规则失败

这类报错信息里会直接写清违反了什么，例如：

```
接口方法缺少 @Operation 注解
写接口缺少 @RequiresPermission
Service 层不得依赖 Controller
```

**这类报错不要绕过**，按提示补注解或调整依赖方向。规则清单见 `AGENTS.md` 的「CI 与本地门禁」章节。

## 五、它和 `ci.yml` 的关系

两者是**同一套检查的两份写法**：

| | 本地脚本 | 云端配置 |
|---|---|---|
| 文件 | `scripts/ci-check.sh` | `.github/workflows/ci.yml` |
| 谁来跑 | 你自己敲命令 | GitHub Actions（当前**不会触发**，因为远程是 Gitee） |
| 现在有用吗 | ✅ **日常就用这个** | 📄 备用：将来迁回 GitHub 时直接生效 |

**改了一边记得改另一边**，保持两边步骤一致。

---

## 六、一句话总结

```bash
bash scripts/ci-check.sh        # 提交前跑一次，看到「全部通过 ✔」就提交
```

如果只改了一小块，用带参数的版本省时间：`backend` / `frontend-lint` / `frontend-build` / `miniapp`。
