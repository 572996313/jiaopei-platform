# 班级正式维护与课次执行变更首批范围

> 状态：**已归档（历史过程方案，不再维护，2026-09-20）**。所述功能已落地，现行页面能力见 `docs/前端交付说明.md`；排课/执行两页后续又有拆分，归档口径勿直接引用。

## 1. 主题定义

下一阶段最小产品主题不是再补一个独立页面，而是在现有两条主线上补出“真正可维护、可处理变更”的感觉：

1. 班级页从“只看主档和成员”升级为“可正式维护班级”
2. 日常教务页从“能排课和点名”升级为“可直接处理课次执行变更”

对应页面仍然沿用当前结构：

- 班级正式维护：`/classes`
- 课次执行变更入口：`/schedule`

## 2. 这期要解决的问题

当前系统已经具备主线雏形，但用户还会明显感觉“能看、能录一点、但不够像正式业务系统”：

1. 班级主档当前能看到课程、班型、容量、主讲，但核心字段还不能作为正式维护动作统一修改。
2. 日常教务当前能新增/编辑排课、点名、结课，但“调课、停课、补课、请假”还没有清晰的产品入口语义。
3. 班级变动通知已经有底座，如果班级主档维护能力不补齐，通知就只能提示问题，不能就地处理问题。

因此这期目标不是扩功能面，而是让用户形成两个稳定认知：

1. 班级出了问题，可以在班级页直接改。
2. 课次发生变化，可以在日常教务里直接处理。

## 3. 首批范围

### 3.1 班级正式维护

首批只收口班级主档里最关键、最常改、且已和后端能力最接近的字段：

1. 课程
2. 班型
3. 容量上限
4. 主讲教师
5. 班级状态
6. 备注

说明：

- `课程 / 班型 / 容量` 解决的是班级主档可维护问题。
- `主讲教师` 解决的是责任归属和后续排课承接问题。
- `班级状态 / 备注` 解决的是“这个班目前是什么状态、为何这么改”的最小管理语义。

其中主讲教师仍优先沿用现有班级教师关系与主讲切换规则，不另起第二套“班级负责人”模型。

### 3.2 课次执行变更入口

首批只做“课次级变更入口”，不做完整的业务子系统拆分。

统一收口到课次详情/编辑动作，可支持以下最小操作：

1. 调整课次日期、时间段、教室、授课教师
2. 把课次标记为取消/停课
3. 为课次填写变更备注
4. 以“新增一节课”的方式补录补课课次
5. 在点名弹窗内继续承接学员请假记录

产品口径解释：

- `调课`：本质是修改既有课次的日期、时间、教室、教师。
- `停课`：本质是把既有课次改为取消状态，并要求备注原因。
- `补课`：首批不做独立补课单，直接通过新增课次承接，并在备注中说明补课背景。
- `请假`：首批不做独立请假审批，继续在课次点名里以 `leave` 状态承接。

### 3.3 班级维护与变更通知联动

这期必须让“通知”和“维护动作”形成闭环：

1. 班级缺课程、缺班型、缺主讲时，可在班级页直接修改主档处理。
2. 主讲发生切换后，班级变动通知可继续作为结果提醒存在。
3. 修改完成后，状态型 notice 会按当前后端规则自动转为 resolved 或不再作为待处理展示。

## 4. 首批明确不做

为了让范围收得住，这期明确不做以下内容：

### 4.1 班级正式维护不做

1. 不做班级历史版本对比
2. 不做班级审批流
3. 不做批量调整多个班级主档
4. 不做自动改写未来所有已排课课次的任课老师/课型逻辑
5. 不做班级财务、课消、结转等经营动作

### 4.2 课次执行变更不做

1. 不做独立“请假管理 / 调课管理 / 补课管理 / 停课管理”四套页面
2. 不做请假审批流
3. 不做请假后自动匹配补课方案
4. 不做调课后自动通知老师/家长
5. 不做复杂连锁改期，例如“一次调整后自动改未来全部同周课次”
6. 不做教师跨校区代课协调流程
7. 不做补课套餐、补课扣次、补课余额等经营规则

## 5. 首批产品口径

### 5.1 班级正式维护的判断标准

只有当用户在班级页能直接完成以下动作时，才算进入“正式维护”而不是“只读展示”：

1. 选中班级后，能修改课程、班型、容量、状态、备注
2. 能在同一页面完成主讲教师调整
3. 修改完成后，班级摘要区立即展示最新结果
4. 班级风险与变动通知会随主档变化同步刷新

### 5.2 课次执行变更入口的判断标准

只有当用户不离开日常教务主页面，就能处理常见课次变更时，才算首批达标：

1. 找到某节课
2. 进入编辑
3. 完成调课或停课
4. 记录变更备注
5. 回到列表继续点名、结课或查看提醒

也就是说，这期目标是“在课次执行上下文里处理变更”，而不是“先搭一个完整流程中心”。

## 6. 页面表达建议

### 6.1 班级页

建议把班级主档区域强化成一个明确动作区：

- 主档摘要
- 编辑主档
- 主讲维护
- 班级主档风险
- 班级变动通知

用户看到后应能理解：

1. 这个班现在是什么状态
2. 缺什么
3. 去哪里改
4. 改完会有什么提醒

### 6.2 日常教务页

建议把当前“新增排课/编辑课次”的语义明确升级为“课次执行变更入口”，页面文案统一围绕以下几类动作：

- 调课
- 停课
- 补课录入
- 点名请假

注意：

- 首批可以共用现有编辑弹窗和点名弹窗，不强求新开模块。
- 重点是入口命名、操作目的和用户感知要清楚。

## 7. 验收口径

### 7.1 班级正式维护验收

1. 教务在班级页选择一个班级后，可以正式修改课程、班型、容量、状态、备注。
2. 教务可以在班级页完成主讲教师切换，不需要绕到其他页面。
3. 修改班级主档后，班级摘要区会回显最新值。
4. 若原来存在 `missing_course / missing_class_type / missing_primary_teacher`，在问题被修复后，页面中的正式班级变动通知会同步收敛。
5. 若主讲发生变化，仍能看到 `primary_teacher_changed` 结果提醒。

### 7.2 课次执行变更入口验收

1. 教务可以在日常教务页对既有课次发起编辑，并修改日期、时间段、教室、授课教师。
2. 教务可以把课次改为取消/停课，并填写变更备注。
3. 教务可以通过新增课次承接补课，不需要单独补课模块也能完成最小业务动作。
4. 教务可以继续在课次点名中记录学员请假，不要求跳到独立请假中心。
5. 课次变更后，列表、日课表、提醒区能回看到最新状态。

## 8. 这期完成后的产品感知

如果这期做完，用户对系统的认知应从：

`这是一个能录数据、能看点名的系统`

升级为：

`这个系统已经能正式维护班级，也能在日常执行里处理课次变化`

这就是本阶段最小但关键的产品跃迁。
