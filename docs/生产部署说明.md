# 生产部署说明

本文档描述当前仓库可运行的试运行/首期生产 Docker 化方案。它用于把现有前后端、MySQL、Redis 组合成可启动环境，不代表已完成正式生产安全加固。

> 部署失败（stash 报 pathspec、端口被占用、容器解析不到 upstream、要复用宿主机已有的 MySQL/Redis）请先按 [生产部署排障手册.md](生产部署排障手册.md) 排查。

## 部署资产

- `backend/Dockerfile.deps`：后端依赖基础镜像，把 Maven 依赖固化进镜像层（不含业务源码）。
- `backend/Dockerfile`：编译打包 Spring Boot 后端，运行时使用 JDK 21 JRE；依赖来自 `backend-deps` 镜像。
- `frontend/Dockerfile.deps`：前端依赖基础镜像，把 `node_modules` 与 pnpm store 固化进镜像层。
- `frontend/Dockerfile`：构建 Vue 前端，并使用 Nginx 托管静态资源；依赖来自 `frontend-deps` 镜像。
- `docker/docker-compose.prod.yml.example`：编排模板（MySQL、Redis、backend、frontend/nginx，以及两个仅用于构建的依赖基础镜像服务 `profiles: ["deps"]`）。**仓库只维护模板，不维护服务器上的运行实例。**
- `docker/docker-compose.prod.yml`：各服务器私有的运行实例，由模板复制生成，已加入 `.gitignore`，`git pull` / `deploy.sh` 永远不会覆盖。
- `docker/nginx/default.conf`：前端静态资源和 `/api` 到 backend 的反向代理。
- `docker/prod.env.example`：统一环境变量模板。

## 运行实例（模板 + 本地实例）

各部署服务器的数据库环境不同（例如已有 1Panel 托管的 MySQL/Redis），因此编排文件采用「模板 + 本地实例」模式，和 `prod.env.example` → `prod.env` 一致：

| 文件 | 归属 | git 跟踪 | 维护方式 |
| --- | --- | --- | --- |
| `docker/docker-compose.prod.yml.example` | 总部 | 是 | 随代码更新 |
| `docker/docker-compose.prod.yml` | 各服务器 | 否（gitignore） | 服务器按环境自行修改 |

首次部署时复制并按本机环境修改：

```bash
cd /mnt/software/jiaopei
cp docker/docker-compose.prod.yml.example docker/docker-compose.prod.yml
# 按需删除内置 mysql/redis 服务、调整端口/数据目录等，见模板头部注释与排障手册场景 D
docker compose -f docker/docker-compose.prod.yml --env-file docker/prod.env config > /dev/null && echo OK
```

总部更新模板后，手动对比合并，pull 不会覆盖本地实例：

```bash
diff -u docker/docker-compose.prod.yml.example docker/docker-compose.prod.yml
```

### 从旧版（compose 受 git 跟踪）切换过来（一次性）

改名提交会从 git 中删除 `docker/docker-compose.prod.yml`。**首次切换不要直接跑 `deploy.sh`**（旧脚本的 stash/merge 会对该文件产生 modify/delete 冲突），在每台服务器上手工执行：

```bash
cd /mnt/software/jiaopei
git config core.fileMode false                                   # 关掉 chmod 造成的“已修改”
cp docker/docker-compose.prod.yml /tmp/jiaopei-compose.local.bak # 备份当前运行配置
git checkout -- docker/docker-compose.prod.yml                   # 放弃对跟踪文件的改动
git pull origin master                                           # 拉下改名 + .gitignore + 新 deploy.sh
cp /tmp/jiaopei-compose.local.bak docker/docker-compose.prod.yml # 恢复为本地运行实例（此时已不被跟踪）
git status                                                       # 应为 clean
./docker/deploy.sh "切换为模板 + 本地实例模式"
```

> 若 `git pull` 因 `docker/deploy.sh` 有内容改动（不只是权限位）而拒绝快进合并，先 `git stash push -- docker/deploy.sh`，pull 完成后再 `git stash pop`。

## 环境变量

先复制模板：

```powershell
Copy-Item docker\prod.env.example docker\prod.env
```

至少修改：

- `DB_PASSWORD`
- `MYSQL_ROOT_PASSWORD`
- 如占用默认端口，调整 `MYSQL_PORT`、`REDIS_PORT`、`BACKEND_PORT`、`FRONTEND_PORT`

说明：

- 后端容器使用 `DB_USERNAME` / `DB_PASSWORD` 连接 MySQL。
- MySQL 容器用同一组 `DB_USERNAME` / `DB_PASSWORD` 创建应用账号，解决本地配置中 `DB_PASSWORD=1234` 与旧 compose `MYSQL_ROOT_PASSWORD=root` 不一致的问题。
- 前端登录后使用登录接口返回的 JWT,`VITE_API_AUTHORIZATION` 默认留空,仅作为特殊对接场景的兜底。

## 构建与启动

推荐使用 `docker/deploy.sh`，它会自动完成「依赖镜像按需重建 -> 构建 -> 启动 -> 健康检查」：

```bash
./docker/deploy.sh "本次发布说明"
```

### 依赖基础镜像（避免每次部署重下依赖）

Maven / pnpm 依赖固化在 `jiaopei-platform-backend-deps:prod`、`jiaopei-platform-frontend-deps:prod` 两个镜像层里。带 tag 的镜像不会被 `docker builder prune` / BuildKit 缓存回收影响，因此源码变更时只重新编译，不再联网重下依赖。

`deploy.sh` 的行为：

- 计算 `pom.xml`、`settings-docker.xml`、`pnpm-lock.yaml`、各 `package.json` 的哈希，与 `/mnt/software/jiaopei/.deps-stamp` 比对；
- 未变化：直接复用依赖镜像（默认，日常部署走这条）；
- 有变化：自动重建依赖镜像后再构建业务镜像；
- 依赖镜像不存在：无论是否加参数都会先构建。

可手动控制的参数：

```bash
./docker/deploy.sh --update-deps   # 强制重建依赖镜像（重新下载依赖）
./docker/deploy.sh --reuse-deps    # 强制沿用现有依赖镜像（离线/依赖暂不更新时）
```

手动构建（不经 `deploy.sh`）时，必须先构建依赖镜像，否则业务镜像的 `FROM` 会失败：

```bash
docker compose --env-file docker/prod.env -f docker/docker-compose.prod.yml --profile deps build backend-deps frontend-deps
docker compose --env-file docker/prod.env -f docker/docker-compose.prod.yml up -d --build
```

说明与排障：

- 两个依赖镜像常驻 `/var/lib/docker`，合计约 1.2–1.5G，部署前先确认磁盘（`df -h /var/lib/docker`）。
- 首次启用本方案或依赖声明变化时，会完整下载一次依赖；这是预期行为，之后仅源码变化的部署不再下载。
- 若编译报「找不到某个依赖」，但 `pom.xml` 里明明声明了，先执行 `./docker/deploy.sh --update-deps` 重建依赖镜像。
- 依赖镜像被替换后，旧镜像会变成悬空镜像，`deploy.sh` 第 6 步会自动清理，不会越积越多。

### 1C1G Ubuntu 低配机建议

1C1G 服务器上不要直接并行构建全部镜像。建议先准备 swap，再串行分步构建。

创建 2G swap 示例：

```bash
sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
free -h
```

低配机建议使用串行构建：

```bash
export COMPOSE_PARALLEL_LIMIT=1
docker compose --env-file docker/prod.env -f docker/docker-compose.prod.yml --profile deps build backend-deps
docker compose --env-file docker/prod.env -f docker/docker-compose.prod.yml --profile deps build frontend-deps
docker compose --env-file docker/prod.env -f docker/docker-compose.prod.yml build backend
docker compose --env-file docker/prod.env -f docker/docker-compose.prod.yml build frontend
docker compose --env-file docker/prod.env -f docker/docker-compose.prod.yml up -d mysql redis
docker compose --env-file docker/prod.env -f docker/docker-compose.prod.yml up -d backend
docker compose --env-file docker/prod.env -f docker/docker-compose.prod.yml up -d frontend
```

后端 Docker 构建默认使用 `backend/settings-docker.xml`，配置了 Maven 镜像源和较低内存的 Maven 参数。若服务器所在网络访问该镜像源不稳定，可以替换该文件中的 mirror，或在 `docker/prod.env` 调整：

```text
BACKEND_BUILD_MAVEN_OPTS=-Xmx384m -XX:MaxMetaspaceSize=192m -Djava.awt.headless=true
```

如果仍因内存不足失败，优先在服务器上本地执行 `mvn -DskipTests package` 产出 jar，再临时改造为运行时镜像；不要在 1C1G 上并行做 Maven 和前端构建。

查看状态：

```powershell
docker compose --env-file docker\prod.env -f docker\docker-compose.prod.yml ps
```

查看日志：

```powershell
docker compose --env-file docker\prod.env -f docker\docker-compose.prod.yml logs -f backend
docker compose --env-file docker\prod.env -f docker\docker-compose.prod.yml logs -f frontend
```

停止：

```powershell
docker compose --env-file docker\prod.env -f docker\docker-compose.prod.yml down
```

如需连同数据卷清理：

```powershell
docker compose --env-file docker\prod.env -f docker\docker-compose.prod.yml down -v
```

## 初始化与访问

启动后 Flyway 会随 backend 启动自动执行数据库迁移。

默认访问：

- 前端入口：`http://localhost/`
- 后端健康检查：`http://localhost/api/health`
- 如果暴露了 `BACKEND_PORT=8080`，也可访问：`http://localhost:8080/api/health`

Nginx 反代规则：

- `/`：前端静态资源，SPA 路由回退到 `index.html`
- `/api/`：反向代理到 `backend:8080/api/`
- `/healthz`：Nginx 容器健康检查

## 最小验收

启动后至少验证：

```powershell
Invoke-WebRequest http://localhost/healthz -UseBasicParsing
Invoke-WebRequest http://localhost/api/health -UseBasicParsing
```

需要鉴权的接口先调用 `POST /api/auth/login` 获取 JWT,再携带：

```text
Authorization: Bearer <accessToken>
```

## 底座改名（阶段四）发布切换步骤

阶段四把底座身份从项目名里拆出来：Java 包 `com.cornerstone.*`、配置前缀 `cornerstone.*`、Redis key 前缀 `cornerstone:`、浏览器 storage key `cornerstone.*`。**库名、表前缀、jar/artifactId、容器与镜像名、环境变量名全部未动**，因此数据库不需要迁移、`prod.env` 不需要改；但会话与登录态会整体失效一次，属破坏性变更，要安排停机窗口。

1. 停应用容器（`docker compose -f docker/docker-compose.prod.yml down`，MySQL/Redis 数据卷不动）。
2. 换 backend / frontend 镜像并先起后端：本次无新增迁移，Flyway 只校验 checksum 后跳过。
3. **清空 Redis 会话**：`docker exec -it jiaopei-prod-redis redis-cli FLUSHDB`。旧 `jiaopei:token:*` 键新进程不再读取，留着只会让人误判会话仍有效。
4. 起前端容器，通知全员重新登录：浏览器里的 `jiaopei.auth.session` 不再被读取，打开即回登录页；导航偏好 `jiaopei-nav-mode`、`jiaopei-menu-preferences` 恢复默认，需重设一次。小程序端 key 同步改为 `cornerstone.mini.auth.session`，学员侧同样掉线一次。
5. 验收：`/api/health` 返回 200（不带 token，证明 `cornerstone.security.public-paths` 绑定生效）；登录后 `redis-cli keys 'cornerstone:*'` 应看到 `cornerstone:token:{jwt}` 与 `cornerstone:user:tokens:{userId}`；不带 token 访问 `/api/system/users` 应 401。
6. 如需临时关模块：环境变量仍是 `MODULE_ORGANIZATION_ENABLED` / `MODULE_EDUCATION_ENABLED`，名字没变。

## 当前生产风险

- JWT 签名密钥 `AUTH_JWT_SECRET` 必须在 `prod.env` 中配置(至少 32 字节随机串),`docker-compose.prod.yml` 未配置时会拒绝启动。
- 未提供 HTTPS、域名证书、WAF、访问限流等边界安全配置。
- 没有生产级日志采集、监控告警、备份恢复、数据库迁移回滚流程。
- `docker-compose.prod.yml` 是单机试运行/首期生产方案，不是高可用架构。
- 前端 `VITE_API_AUTHORIZATION` 兜底头默认留空,联调时如需固定请求头可通过该构建参数注入。
