# 接口链路与系统运作说明

> 状态：**一期样例已落地（2026-11-24，菜单 V118 / core V120，接口 `GET /api/system/endpoint-chains`）**。目标读者是**实施 / 运维工程师**：点开一个按钮，能顺着看到它背后的接口、控制器、服务与数据表。
> 现行口径以 AGENTS.md 为准；本文只回答"链路能看到什么、看不到什么、为什么不能把它当执行记录"。

## 1. 要解决的问题

用户 2026-11-24 口径：**"给一个接口或一个按钮，能不能把里面的逻辑给流程，让实施人员知道系统怎么运作、会涉及什么东西、逻辑是怎么写的。"**

结论是拆成三层，而不是把代码自动画成流程图：

| 层 | 回答什么 | 能不能自动 |
| --- | --- | --- |
| 1. 固定骨架 | 所有接口都走哪条路（过滤器 → 控制器 → 权限切面 → 服务 → 事务 → Mapper → 库 → 统一响应 → 操作日志） | 讲一次就够，不需要工具 |
| 2. 单接口差异 | 这个按钮走哪个控制器、哪个服务、声明依赖哪些表 | **能**，本期已做 |
| 3. 业务规则 | 什么条件下不允许、按什么公式算、改完牵连谁 | **不能**，只能人工提炼；`@Operation.description` 已经写了一部分 |

## 2. 本期做了什么

系统设置 → **接口链路**（`/system/endpoint-chain`）。D 型只读页：左侧模块分组的接口清单，右侧四段链路。

| 方法 | 路径 | 用途 | 权限 |
| --- | --- | --- | --- |
| GET | `/api/system/endpoint-chains` | 全部接口的静态链路；进程内缓存 60 秒 | `system:endpoint:read` |

每个接口返回五类信息，全部运行时推导，**零新表、零手工登记**：

| 内容 | 来源 |
| --- | --- |
| HTTP 方法 / 路径 / `@Operation` 说明 | `RequestMappingHandlerMapping` + 注解 |
| 权限码 | 方法级 `@RequiresPermission`，其次类级 |
| 界面按钮 | 各模块 `ActionCatalogContributor` 的登记（中文名、说明、是否高危） |
| 控制器方法 | `HandlerMethod` |
| 服务类 | 反射读控制器字段；沿类型名以 `Service` 结尾的字段继续向下（最多 3 层） |
| 数据表 | 服务字段里的 `BaseMapper<Entity>` 泛型 → `@TableName`；表注释取数据字典 |

搜索框覆盖按钮名、权限码、路径、控制器、服务、表名与表注释——**直接搜表名就是反查"哪些接口会碰这张表"**。数据字典每张表头新增「看接口」按钮，带着 `?table=表名` 跳过来并自动填入搜索框，两页互补。

## 3. 口径：声明依赖 ≠ 实际调用

这是本页最重要的一条，页面副标题与响应里的 `note` 都写死了：

- 反射只能知道"这个服务持有这些 Mapper"，**不知道某一次请求实际用了哪几个**。
- 因此表只表示"可能涉及"，**不区分本次读了还是写了**。
- 同一服务上的多个接口会看到同一批表，这是类级依赖的必然结果，不是数据错误。样例里「重算发生额」会列出 `jp_campus`、`jp_student_parent`，是因为 `FeeLedgerServiceImpl` 持有对应 Mapper，不是因为这次点击真的读了这两张表。
- 同一服务接口有多个实现时，链路会把它们都列出来；这是"声明依赖"口径下的保守展开，不是重复 bug。
- **不能把它当审计日志用。** 真要看实际执行，走操作日志或后续的运行期录制（默认关闭、测试环境、脱敏、自动过期），一期不做。

首次调用要遍历 65 个控制器的依赖，本机约 2–3 秒；结果缓存 60 秒，后续打开是秒开。

## 4. 样例验收（2026-11-24 本机实测）

接口链路返回 **267 个接口 / 176 个带权限码**，模块分布与数据字典一致。以「收费台账 → 重算发生额」为例：

- 按钮：`重算发生额`（`education_fee_ledger`，高危），权限码 `education:fee:write`
- 接口：`POST /api/education/fee-monthly/recalculate`
- 控制器：`FeeMonthlyController#recalculate`
- 服务：`FeeLedgerServiceImpl`、`FeeMonthlyServiceImpl`
- 可能涉及（12 张）：`jp_fee_ledger`、`jp_fee_ledger_item`、`jp_fee_monthly`、`jp_fee_payment`、`jp_fee_attendance_month`、`jp_fee_item`、`jp_class`、`jp_class_student`、`jp_student`、`jp_student_parent`、`jp_term`、`jp_campus`

链路推导中踩到并已修掉的一处 Spring 行为：`RequestMappingHandlerMapping.getHandlerMethods()` 里的 `HandlerMethod` 可能是**懒解析形态**，`getBean()` 返回的是 bean 名字符串而不是控制器实例，必须先 `createWithResolvedBean()`。这行注释留在实现里，避免后人重踩。

## 5. 不能自动的那部分

`FeeLedgerServiceImpl` 有 941 行、13 个 Mapper。把它自动画成流程图出来的是几十个节点的蜘蛛网，实施人员看不懂；真正想知道的"什么条件下不允许""按什么公式算"不在调用关系里。

可行的补充顺序：

1. 先把 `@Operation` 的 `summary` + `description` 原样展示（本期已做）。这批文案是开发写在代码旁的，比事后补文档可靠。
2. 按 5 个典型模式各写一个"人话"范例：单表 CRUD / 主子表 / 跨模块校验 / 状态机 / 算账重算。每个范例回答"点哪、读哪几张表、写哪几张表、哪几步是算账"。
3. 一期不够用再评估**方法级**调用链：ArchUnit 是 test 作用域，运行期没有，要么加 ASM 运行时解析，要么加构建步骤——成本明显上升，先不付。

## 6. 已知边界

| ✅ 能做 | ❌ 不能做 |
| --- | --- |
| 按钮 → 权限码 → 接口 → 控制器 → 服务 → 表 | 某一次请求实际读了/写了哪几张表 |
| 同一张表被哪些接口"可能涉及" | 判断这次调用会不会成功、会不会回滚 |
| 展示开发写好的 `@Operation` 业务说明 | 自动推导计费公式、冲突判定、状态流转 |
| 模块关闭后链路自动消失 | 用页面代替代码评审或审计日志 |

## 7. 发布注意

权限快照在登录时写进 JWT 与 Redis 会话，新码 `system:endpoint:read` 对**已登录的旧会话无效**——发布后需重新登录一次，否则菜单能看到、点进去 403。菜单与角色授权由 **V118（教培）/ V120（底座基线）** 双轨种入，内容一字不差。
