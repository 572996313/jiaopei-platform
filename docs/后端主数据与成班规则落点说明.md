# 后端主数据与成班规则落点说明

## 1. 当前仓库主数据覆盖结论

当前 `backend` 已落地的教育主线主要集中在：

- 教师档案：`jp_teacher`
- 学员档案：`jp_student`
- 班级主档基础版：`jp_class`
- 报名与入班：`jp_class_student`（V109 起报名并入名册，原 `jp_enrollment` 已删除）
- 排课与课次执行：`schedule_lesson`、`schedule_teacher_rel`、`jp_attendance`

这意味着“排课 -> 课次 -> 点名”链路已经有底座，但档案中心与成班规则层仍明显偏薄。

## 2. 重点缺口清单

### 2.1 课程

- 当前状态：仓库中没有 `course_category` / `course` 实体、迁移、mapper、接口。
- 直接影响：
  - 班级主档无法明确归属到课程。
  - 排课与成班无法按课程维度做筛选、规则判断和统计。

### 2.2 班型

- 当前状态：没有 `class_type` 主数据。
- 直接影响：
  - 一对一、小班、大班等差异无法结构化表达。
  - 成班人数阈值和排课/执行差异没有落点。

### 2.3 班级主档

- 当前状态：已有 `jp_class`，但仍是基础版。
- 已有字段：机构、校区、学期、班级编码/名称、单一 `teacher_id`、容量、状态。
- 缺口：
  - 缺少 `course_id`、`class_type_id`。
  - 仍以单一 `teacher_id` 承接老师，无法表达主讲/助教/阶段性换老师。

### 2.4 班级教师

- 当前状态：只有课次维度的 `schedule_teacher_rel`，没有班级维度的长期教师关系。
- 直接影响：
  - 只能知道“某节课谁来上”，不能稳定记录“这个班平时由谁负责”。
  - 老师调整后，无法和成班/排课/点名联动提示结合。

### 2.5 家长联系人

- 当前状态：学生表只有 `guardian_name`、`guardian_phone` 两个平铺字段。
- 直接影响：
  - 无法承接多个联系人。
  - 无法表达关系、主联系人、紧急联系人、微信等扩展信息。

### 2.6 成班规则配置

- 当前状态：仓库中没有规则表，也没有规则作用域模型。
- 直接影响：
  - 目前只能把“几人成班”写在口头规则里，无法留痕配置。
  - 无法按校区/课程/班型/老师做差异化。

### 2.7 变动影响提示

- 当前状态：仓库中没有“前置变更导致下游需复核”的承接对象。
- 直接影响：
  - 即使后面新增规则，也没有地方记录“班级人数变了，需要复核排课/点名/执行计划”。

## 3. 本轮已补的后端底座

本轮没有继续铺控制器和完整流程，而是先把低风险、可直接承接后续开发的骨架补齐：

- 新增迁移：`backend/app/src/main/resources/db/migration/V11__add_master_data_foundation_tables.sql`
- 新增主数据/规则相关表：
  - `jp_course_category`
  - `jp_course`
  - `jp_class_type`
  - `jp_student_parent`
  - `jp_class_teacher`
  - `jp_class_opening_rule`
  - `jp_class_change_notice`
- 补齐 `jp_class` 对课程、班型的关联字段：
  - `course_id`
  - `class_type_id`
- 新增对应 entity / mapper 骨架，供下一步 service、controller、页面接入直接复用。

## 4. 成班规则配置的最小设计落点

首期不做自动引擎，先做“规则可记录、差异可识别、影响可提示”。

### 4.1 规则表落点

`jp_class_opening_rule`

建议首期承接这些最小维度：

- `institution_id`
- `campus_id`
- `course_id`
- `class_type_id`
- `teacher_id`
- `rule_name`
- `min_students`
- `max_students`
- `allow_pre_open`
- `impact_scope`
- `priority_no`
- `status`

说明：

- 这套设计允许默认规则和特殊规则并存。
- `campus/course/class_type/teacher` 允许为空，用于表达“机构默认规则”。
- 后续按优先级从细到粗匹配即可，不必首期写死判断引擎。

### 4.2 最小判定策略

首期建议后端只做半自动判定：

1. 读取班级主档的 `course_id`、`class_type_id`、老师关系。
2. 找到最匹配的一条成班规则。
3. 结合 `current_students` 判断是否低于阈值、是否超上限、是否允许先开班。
4. 不直接强制改状态，先产出提示对象。

## 5. 变动影响提示的最小设计落点

`jp_class_change_notice`

建议把它作为“下游复核待办”来承接，而不是首期就做复杂消息中心。

首期最小字段：

- `class_id`
- `source_type`
- `source_id`
- `notice_type`
- `notice_level`
- `notice_status`
- `notice_message`
- `suggested_action`

建议首期支持的来源：

- `class_student`
- `class_teacher`
- `class_base`
- `opening_rule`

建议首期支持的提示类型：

- `recheck_opening_rule`
- `review_schedule`
- `review_attendance_scope`
- `manual_follow_up`

## 6. 下一步建议

下一步优先级建议如下：

1. 先补 `课程/班型/家长联系人/班级教师` 的最小 CRUD，保证档案中心可维护。
2. 再把 `TeachingClass` 的创建/查询扩到 `course_id`、`class_type_id`。
3. 在班级学员、班级教师变更时，写入 `jp_class_change_notice`。
4. 最后再补“按规则匹配 + 生成复核提示”的 application service。

这样能把范围控制住，同时又给前端深化后的工作台和教务中心提供后续真实数据来源。
