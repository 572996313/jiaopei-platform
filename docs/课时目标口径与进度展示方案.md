# 课时目标口径与进度展示方案

状态：**已落地**（2026-09-27 开工并验收通过，V79 已应用到本机库）。原「待拍板」四条按第 10 节的记录直接定了，没有等回复；第 13 节是落地时对本文的偏离，以第 13 节为准。

## 1. 要解决的问题

现在班级只有一个目标字段：`jp_class.weekly_lessons`（每周应上几节），完成度报表拿它当分母，补排引擎按它算缺口。

问题是操作员手上往往没有"每周几节"这个数。他知道的可能是：

- "一个月上 8 次课"
- "这个班一共 40 节课，上完就结课"
- "每周三、周六各一节"（这个才是周口径）

让人自己去算"8 ÷ 4.3 ≈ 每周 2 节"，多数人不会算、算了也不信，最后干脆空着不填 —— 空着就没有缺口提示，自动补排对这一整批班失效。

## 2. 结论：分母和进度是两个字段，各喂各的

| 用户知道的 | 填哪 | 落到哪 | 谁读它 |
| --- | --- | --- | --- |
| 每周 N 节 / 每月 N 节 | 周目标（可选"按月填"，系统换算） | `weekly_lessons` | 完成度分母 → 补排缺口 |
| 整班共 N 节 | 总课时 | `total_lessons` | 只做课时进度，**不进分母** |

**两栏互不排斥，可以同时填。** 这是最常见的真实情况：合同 40 节课、每周上 2 节。所以总课时不是"周目标的替代口径"，而是一个独立维度 —— 早期草稿把它做成三选一，会把最有用的那种组合排除掉，已改。

**为什么"整班共 N 节"不摊到周**：40 节课可以一周 2 节上 20 周，也可以一周 4 节上 10 周，摊法只取决于上课节奏 —— 而节奏是排课计划里已经写着的东西，不是总课时能推出来的。硬摊出来的"本周应排 3 节"是系统编的数，操作员一旦发现"它报缺课但这周我本来不打算上"，整张报表的可信度就没了。

## 3. 数据模型

`jp_class` 加三列（迁移 `V79__add_class_lesson_target_input_and_total.sql`）：

```sql
ALTER TABLE `jp_class`
    ADD COLUMN `weekly_lessons_mode`  VARCHAR(16) NOT NULL DEFAULT 'weekly'
        COMMENT '每周应上节数的录入口径(weekly=按周填,monthly=按月填由系统换算)' AFTER `weekly_lessons`,
    ADD COLUMN `weekly_lessons_input` INT NULL
        COMMENT '每周应上节数的录制原值(mode=monthly 时存的是每月节数,换算结果在 weekly_lessons)' AFTER `weekly_lessons_mode`,
    ADD COLUMN `total_lessons`        INT NULL
        COMMENT '整班总课时(合同/教学计划的总节数,NULL=未设定;只用于课时进度,不进完成度分母)' AFTER `weekly_lessons_input`;
```

- **`weekly_lessons` 的含义和读法一个字都不改**，仍是完成度分母的唯一来源。报表 Service 的分母判定、补排引擎、`denominatorSource` 枚举全部零改动。
- `weekly_lessons_mode` **只修饰 `weekly_lessons`**，不描述总课时 —— 列名把这个从属关系写死，就是为了不让人误以为它是全局的"目标口径开关"。它存在的唯一理由是：编辑弹窗要能还原"我当时填的是每月 8 节"，而不是让用户面对一个自己没填过的 2。
- 换算在**保存时**做一次并落 `weekly_lessons`，同时保留原值。只换算一次不留原值的后果：班级日期一改、课再上几节，那个数就悄悄烂在库里没人知道。
- `total_lessons` 与前三列无任何判定关系，独立可空。
- 存量回填：`weekly_lessons` 有值 → `mode=weekly`、`input=weekly_lessons`；为 NULL → 保持 `mode=weekly`、`input=NULL`。不新增 `none` 一档，少一个状态要判。
- 三个字段都要配 `@TableField(updateStrategy = FieldStrategy.ALWAYS)`（照现有 `weeklyLessons` 的写法）：`updateById` 默认忽略 null，不配就**清空不了**，用户把总课时删掉会发现它又回来了。

## 4. 换算规则（要能印在界面上）

| 录入 | 公式 | 例 |
| --- | --- | --- |
| 每周 N | `weekly = N` | 3 → 每周 3 节 |
| 每月 N | `weekly = round(N × 12 ÷ 52)` | 8 → 96 节/年 ÷ 52 周 = 1.85 → **每周 2 节** |
| 总课时 N | 不换算，只写 `total_lessons` | 40 → 只出进度 |

- 一年 52 周写死成常量，**不用 4.348 那种小数**：算式要能让人拿计算器复验，`8 × 12 ÷ 52` 一眼看得懂，`8 ÷ 4.348` 看不懂。
- 取整用四舍五入，不用向下取整。向下会让"每月 8 节"变成"每周 1 节 ×52=52 节/年"，一年少算 44 节，报表长期报不出缺口。
- **换算只对"每周 ≥1 节"的中高频班成立**，这是这套口径固有的天花板：每月 4 节 → `48÷52=0.92` → 1；每月 2 节 → `24÷52=0.46` → **0**。低频班一换算就塌成 0 或 1。处理：
  - 结果为 0 时 `weekly_lessons` **写 NULL**，`input`/`mode` 照原样保留（用户的"每月 2 节"不能丢），界面显示"每月 2 节，不足每周 1 节，未设周目标"。
    注意这里**不是**因为"写 0 会被读成这周不该排课"—— 全仓库唯一读 `weekly_lessons` 的地方是 `ScheduleCompletenessServiceImpl#buildRow`，判定是 `target != null && target > 0`，写 0 的实际效果与 NULL 完全一样：静默回落到计划展开。之所以仍要写 NULL，是因为 0 在本项目语义里是非法值（AGENTS 的课时目标口径条目），存一个和"没存"等价、但字面上会误导下一个读代码的人的值，没有好处。
  - 每月 1~4 节这类低频班，引导用户改填总课时看进度，或者干脆不填周目标、让报表走 `plan_expand` 兜底档。
- 换算结果只在界面上显示，不另存注释字段；`weekly_lessons` 存的就是换算后的整数，读它即所得。

## 5. 课时进度（新增展示，不参与算账）

放在完成度页班级列的副行。

- **分子**：该班**日期已过（`lesson_date < 今天`）且未停课（`lesson_status != 'cancelled'`）**的课次总数，与 cell 匹配无关的全量统计。
  这里有个必须写死的区别：完成度的格子 `WeekCell.completed` 是**按"日期+节次"格子匹配**数出来的，计划外上的课、补课另排的格子不落在应排格上，不计入那个数。进度要的是"这个班一共上了几节"，两种口径不能混用。
  因此响应字段与界面标签必须与「已完成」（cell 级 matched count）在字面上错开 —— 同一页出现两个都叫"已完成"、数字还不一样的列，一定会被当 bug 报上来。落地取的名是 `heldLessons` + 标签**「已上课」**（口径见第 10 节第 1 条：日期已过且非已停课，不要求点过结课）。
- **分母**：`total_lessons`。为空则整块进度不渲染（不是显示 0/0）。
- **预计结课日**：剩余节数 ÷ 近 4 周实际平均每周上课节数。
  `jp_class` 只有 `opened_at`（开班日期），**没有结课日期列**，所以这只能是推算值，界面写"预计"，别写得像承诺。
- **有价值的不是这个日期本身，是它和计划结课日的差**：推算出的结课日晚于该班启用中计划的最晚 `end_date` 时，说明"按现在的节奏上不完 40 节"，标出来提示一句。这比单独显示一个日期有用得多，也是总课时这一栏真正要回答的问题。

## 9. 明确不做

- **不做逐周递减**（剩 N 节 ÷ 剩 M 周，每周应排数都在变）。它更贴近"结课前刚好上完"，但同一张表里上周该排 3、这周该排 4，操作员必来问，得把算式印进每个单元格才解释得清 —— 收益不值这个解释成本。
- **不做自定义周期**（按季度、按学期）。先拿"总课时 + 每月"顶住，真出现第三种口径再说。
- **不把 `weekly_lessons` 改成派生值/不落库**。报表和引擎都读它，改成每次现算等于把上面两条的坑一起挖回来。
- **不让 `total_lessons` 参与缺口、补排、任何分母计算**。它一旦开始影响算账，第 2 节那条"各答各的问题"就作废了。

## 10. 四条口径的落地选择（用户授权自行决策，事后逐项复查）

1. **进度分子取"日期已过且非已停课"**，标签因此叫**「已上课」**而不是「已结课」。理由：大量机构只点名不点结课，只算 `completed` 会让进度长期偏低、看着像没上课；进度是给人看个大概的，不该要求操作员每次都点结课。代价是这一栏与 cell 级「已完成」的差更明显，所以两处文案刻意错开、完成度页口径块里写明"已上课不按格子匹配"。
2. **不加双周口径**。低频班（每月 1~4 节）换算到周会塌成 0 或 1，现在的处理是"塌 0 写 NULL、`input` 留原值、界面说明原因"，并引导去填总课时或让报表回落 `plan_expand`。真加一档双周要把分母从"每周"变"每两周"、完成度的列也要从自然周改成双周格 —— 比本方案大一倍，等客户反馈再说。
3. **四舍五入的偏差写在表单回显里**，不做额外列：每月 8 节 → 回显"每月 8 节 ≈ 每周 2 节（8×12÷52=1.85，四舍五入），报表按每周 2 节算"。操作员看得见算式也看得见取整后的分母来源，不需要再补一句"一年约 104 节"。
4. **未设周目标的班不额外标一句**，沿用行上已有的「按计划展开」标签。理由是这一行标签说的就是"这一行的分母从哪来"，再加一句"缺口按排课计划算"是同义重复；真出问题的是标签看不懂，那属于文案批次。

## 13. 落地时对本文的偏离（以此为准）

1. **进度字段名 `heldLessons`、标签「已上课」**（本文原写 `finishedLessons` / 「已结课」）。第 10 节第 1 条选了"日期已过即算"，那就不是"结课"，名字必须跟着口径走。
2. **`ClassRow` 多带一个只读字段 `planEndDate`**（该班启用中计划的最晚 `end_date`）。"推算结课日是否晚于计划"这句判断放前端做，后端只给两个日期；否则换一个展示口径就要改后端。
3. **算式串由前端镜像公式生成，后端不提供 `describe()`**。回显是"每月 8 节 ≈ 每周 2 节（8×12÷52=1.85，四舍五入）"这种展示串，`Math.round(input*12/52)` 与后端 `BigDecimal HALF_UP` 对 `3×input/13` 永不落在 `.5`（6 不整除 13 的奇数倍），两边取值必然一致。**代价：改公式要两边同改**，已写进 AGENTS.md 的课时目标条目。
4. **进度分子只按 SQL 的 `lesson_date < 今天` 过滤，`cancelled` 在内存里过滤**。Mockito 的 `selectList(any())` 会忽略 wrapper 条件，把日期判断再写一遍到 Java 里就只是为了让测试好看，属于多余的防御。
5. **`LessonTargetConverter` 多一个 `normalizeMode(mode)`**（空→weekly，未知值报 `BAD_REQUEST` 并列允许值）。原设计只列了换算，但 mode 是请求直接进来的字符串，不在写入口校验就会把脏值存进列。
6. **预计结课日的速率取"近 4 周实际平均每周节数"**（常量 `RECENT_RATE_WEEKS = 4`），剩余 ≤0 或速率为 0 时返回 null、界面不显示推算日期 —— 宁可空着也不给一个假精度的日子。
