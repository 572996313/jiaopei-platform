### 导航编排（底座 system；菜单 V93 / core V111，双轨内容一字不差）

交付后客户自己调侧边栏：组名、组图标、组间与组内顺序、页面属于哪个分组、某一页是否在侧边栏显示。**这一页是 `sys_menu` 的受限视图，只有那五列可写**；路由、权限码、节点类型、编码仍归「菜单管理」——那是平台管理员的工具，改错了就是"入口指到不存在的页面"或"把人挡在 403"，而现场操作员无从判断。

| 方法 | 路径 | 用途 | 权限 |
| --- | --- | --- | --- |
| GET | `/api/system/navigation` | 管理端可编排的目录与页面（不含按钮、不含其他端），每个节点带 `locked`（底座段只读）与 `grantedRoleCount`（被几个在职角色勾到） | `system:nav:manage` |
| PUT | `/api/system/navigation` | 整批保存这五列；**全部校验通过才落库**（半批生效会和前端草稿对不上且不报错） | `system:nav:manage` |
| POST | `/api/system/navigation/catalogs` | 新建顶层分组：立即写库，**同事务授权给所有在职角色**，返回新节点 id、授权角色数与最新结构 | `system:nav:manage` |

校验只拦"改完找不到这一页"那一类，四条实现口径别改回去：

- **「系统设置」整棵子树只读**（`menu_code=system` 往下一律 `locked`）。用户管理 / 角色管理 / 机构资料后端还没比机构范围（AGENTS「安全与数据一致性约定」第 8 条），允许客户把它们的页面挪进业务分组，等于绕过"不给非平台角色开系统设置页"这条硬约束。
- **侧边栏只到两层**：顶层目录不许再套进目录、已经在目录里的目录不许当父级、页面不许挂进底座段。
- **顶层入口不许同名**（含顶层散页）：两颗一样的图标等于白改，保存与新建两处都拦。
- **目录不给"隐藏"开关**：`buildTree` 会把父节点未授权的子节点提升到根，藏一个目录等于把它下面的页面炸成一排散页图标。要藏一整组就把组里的页面逐个隐藏；组里没有可见页面时这一组自动不显示。
- `SystemMenuEntity` 的 `parentId`/`icon` 配了 `@TableField(updateStrategy = FieldStrategy.ALWAYS)`：父级传 NULL 是"提升为顶层分组"，否则 `updateById` 会静默忽略 null（AGENTS「安全与数据一致性约定」第 5 条）。
- **结构改动不踢会话**：导航树每次进系统现拉（`/api/auth/current/menus`），保存后只刷新操作者自己的侧边栏，别人下次进入才看到。这里没碰权限码，所以不存在"旧权限在令牌过期前继续可用"的问题——但**这一页自己的码改动仍要重登**（权限快照写进 JWT）。

### 编号规则（底座 system；建表 V88 / core V108，菜单 V90 / core V109，默认启用 V91 / core V110）

主数据编码不再靠手填：格式是 `前缀 + 日期段 + 序号`，不含随机字符，**允许断号**（不建号表、不加行锁，客户并发低）。资源清单由代码登记决定，不是由表里的行决定——业务模块用 `CodeRuleContributor` 登记自己的资源，底座只认登记过的资源码。

后两条刻意不设权限码：服务的是每个主数据新增页上那颗按钮与那条预填，教师也要给自己填工号，挂 `system:*` 等于逼机构去勾一个他不一定有的系统页。

语义（`CodeRuleService`）：

- **PC 表单永远提交"看得见的号"**。新增弹窗打开时 `CodeInput` 就调 `/next` 把建议号填进输入框（只读、不落库，取消弹窗不消耗号），操作员存下去的就是眼前这个数；想换点「重新生成」，想自己填直接改。**不做"留空、保存时后端悄悄补一个"**——用户 2026-09-28 明确否决：编号是客户要看得见的内容，藏着生成会被骂。
- **`resolveForCreate` 的留空补号只服务没有编号输入框的入口**：小程序自助建档（`autoCodeIfEnabled`，家长端根本没有这一栏）以及后续接口直连。PC 侧编码一律必填；未启用或没配过规则时空值报中文「XX编号不能为空」。因此 12 个创建 DTO 上的 `@NotBlank` 已下沉到 Service（守护：`CodeRuleWiringTest`），让"无人值守入口留空即补号"与"PC 漏填要报错"各走各的判空。
- 操作员自己填了就直接存他填的（只 `trim`），不比对格式、不查是否撞规则。
- 建议号撞库时最多顺延 20 次（`MAX_COLLISION_ATTEMPTS`）；撞满报「XX当前号段已无可用编号,请加大序号位数或改日期段粒度」。`/next` 打在没启用的资源上报「XX未启用自动编号,请手工填写」。
- 编辑弹窗的编码必填且不预填：整表单覆盖，留空不等于"再要一个新号"。
- **12 条规则默认全部启用**（V91；建表时是"不写行=未启用"，结果全站看不见这个功能，现场反馈成"编号没实现"）。core 侧 V110 **只种底座自己登记的 `institution`**，其余 11 条是教培的行业资源清单，写进底座迁移等于把资源表塞给第二个消费方（守护：`ExternalIdVocabularyGuardTest` 扫 core 目录的 SQL）——新项目要开箱有号，在自己项目的迁移里补自己那批。两份都用 `INSERT IGNORE` 撞唯一键 `uk_sys_code_rule_resource`，所以现场已在页面上改过格式或手动停用过的资源**不会被覆盖**，只补缺的。

### 用户账号注销（底座 auth；列表按钮教培 V94 / core V112，双轨内容一字不差）

小程序端早有自助注销，PC 侧补齐为**管理员在「系统管理 → 用户管理」代注销**（没有 PC 自助注销入口）。按钮走配置化而不是硬编码：`sys_list_config`(`system-users`) 的 `actions_json` 第七条 `user-deregister`，权限沿用 `system:user:manage`，**不新增权限码、不新增菜单节点**。

| 方法 | 路径 | 用途 | 权限 |
| --- | --- | --- | --- |
| DELETE | `/api/system/users/{id}` | 注销账号：物理删账号行，连带清掉角色关联与注册凭证，业务档案解除归属 | `system:user:manage` |

四道守卫，缺一条就会把系统注销成进不去的状态：

1. **不能注销当前登录的账号**——把自己关在门外。前端同时把这颗按钮在自己那一行置灰，后端仍照样拒。
2. **只能注销本机构的账号**，持 `PLATFORM_ADMIN` 角色者豁免（与上面第 8 条同一口径；这条是注销链路自己比对了 `AuthContext`，不代表列表与建号已补上）。
3. **必须先停用、再注销**：启用中的账号点「注销」只回一句中文提示，不发请求。注销是毁灭性且不可逆的操作，两段式让人先确认"这人确实不再需要进来了"。
4. **不能注销最后一个可用的平台管理员**：判据是除目标以外还有没有 `status=active` 的 `PLATFORM_ADMIN` 持有者，一个都不剩就拒绝。

执行顺序固定为**失效会话 → 清引用行 → 删账号**，全程 `@Transactional`：

- 先 `invalidateUserSessions(id)`——账号行没了以后，残留 JWT 里的权限快照就没人能复核了。
- **物理删而非逻辑删**：`uk_jp_user_username(username, deleted)` 含 `deleted`，软删行会永久占住这个账号名，"注销后用同名重建"直接撞键（AGENTS「安全与数据一致性约定」第 3 条）。
- 指向 `sys_user_account` 的外键有五张表，删账号前必须全清，否则 1451：`sys_user_role_rel`、`sys_auth_invitation` 底座自己清；`jp_user_student_rel`、`jp_wechat_binding`、`jp_user_campus_pref` 由底座发 `UserAccountDeregisteredEvent`、各业务模块的监听器清（同事务、任一失败整体回滚）。**新增指向账号的表要同批补一条 `physicalDeleteByUserId`**，漏了不是静默失败而是注销直接报错。
- 教师/学员档案是 `releaseOwnerByUserId`（解除归属），**不删行**——历史课次与考勤要挂得住。

小程序自助注销与管理端代注销**共用同一个监听器**，业务侧的清理只维护一份。前端对"启用中"的账号不做置灰而是点击即提示：灰态没有 tooltip，只会让人以为按钮坏了。


自动排工要能落地，先补四件人算不清的事：目标、上限、禁日、占用兜底。这批改的都是"手工排课也照用"的地基，不是排课算法本身。

| 能力 | 落点 | 判定 |
| --- | --- | --- |
| 班级课时目标 | `jp_class.weekly_lessons`（V75） | 完成度报表的分母：设了目标就按"每周应上 N 节"统计，未设（NULL 或 0）回落计划展开 |
| 课时目标录入口径 | `jp_class.weekly_lessons_mode` + `weekly_lessons_input`、`total_lessons`（V79） | `mode=monthly` 时 `weekly_lessons = round(input × 12 ÷ 52)`，只在保存时换算一次、原值保留供表单回显；换算不足 1 节则 `weekly_lessons` 写 NULL（不做"这周不该排课"的假判定）。`total_lessons` **只喂课时进度**，与分母无任何判定关系 |
| 教师负载上限 | `jp_teacher.max_weekly_lessons` / `max_daily_lessons`（V75） | **只提示不拦**，进 `notices` |
| 校区日历停排日 | `jp_school_calendar_day`（V76） | **只提示不拦**；`campus_id=0` 表示全校区，读取按 `campus_id IN (0, 本校区)` |
| 教室禁排 | `jp_schedule_rule.target_type` 扩 `classroom`（V77） | **硬拦**，与班级/教师禁排同一套「星期×节次」格子判定 |

- **提示（`notices`）与冲突（`conflict=true`）是两层**：禁排规则与同时段占用会拦下保存；教师超课时、学员跨班撞课、课次落在停排日只把话摆出来，操作员自己决定继不继续。手工新增/编辑课次弹窗第一次点保存只展示提示，再点一次即放行；批量向导在预览页分块列出。
- **这三列用 NULL 表示"未设定"，不用 0**：与 `capacity_limit` 的"0=不限"故意不同——每周应上 0 节、课时上限 0 节都是非法值。业务侧一律判 `值 != null && 值 > 0`，前端表单留空即取消（实体上配 `@TableField(updateStrategy = ALWAYS)`，否则 `updateById` 会把 null 忽略掉）。**运行时实况**：读完 `weekly_lessons` 的地方带 `> 0` 守卫，所以写 0 与写 NULL 行为完全一致（都是静默回落计划展开）；仍然规定写 NULL，是因为 0 是本项目的非法值，存一个"与没存等价、但字面会误导下一个读代码的人"的值没有好处。
- **教师占用没有唯一键可兜**：班级/教室占用由 V72 的生成列唯一键守，教师跨 `schedule_lesson` + `schedule_teacher_rel` 两表建不了。所以写课次前在事务内按教师 ID 升序 `SELECT id ... ORDER BY id FOR UPDATE` 取行锁（`ScheduleTeacherLock`），升序是为了两个并发会话不会互相持有对方要的锁而死锁。
- **自动排课表的标识约定**：真上排课引擎时（V78 已落），新表统一在名字里带 `auto_` 段（`jp_schedule_auto_batch` 批次表）。校历是校区日历，与自动排课无关，不带 `auto_`。

### 按缺口补排引擎（V78）

一期只做**补排**：拿完成度报表算出的缺口 + 未来窗口里的空位，自动填进课表，**不新建也不修改周期排课计划**。判据是"改计划会把人工设定的周期覆盖掉，而且撤销时分不清哪一格是机器改的"。

| 接口 | 作用 | 关键口径 |
| --- | --- | --- |
| `POST /api/education/schedule-auto-batches/preview` | 出草案，不写库 | 与 `/run` 各算一遍引擎，确认到执行之间若有人插了一节课，以 `/run` 为准 |
| `POST /api/education/schedule-auto-batches/run` | 落库建批次 | 草案为空**不建批次行**（清单里不会长出 0 节的记录） |
| `GET /api/education/schedule-auto-batches` | 批次清单（按校区，最新 20 条） | 只读，`education:read` |
| `DELETE /api/education/schedule-auto-batches/{id}` | 整批撤销 | 只删**本批生成且还没上过**的课次（`lesson_date >= 今天` 且状态在占用档内）；已上课/已完成的原样保留，返回体说清删了几节、留了几节、为什么留 |

- **批次归属落在课次，不落在计划**：`schedule_lesson.auto_batch_id` 记"这一节是哪一批生成的"。**没有**往 `jp_schedule_plan` 加 `auto_batch_id`——一个计划的缺口会分多批补，计划行没有"哪一批"这个身份，而撤销要判的是单节课次。引擎写的课次 **`plan_id` 留空**：报表的缺口条目不带计划 ID，猜一个会让"撤销计划课次"按 `plan_id` 删除时误伤补排队。
- **约束分级与手工排课不同**：教师周/日上限对手工只是提示，对引擎**升格为硬约束**（机器没有人"就知道这样不合适"的判断力，超了会静默铺满教师）；停排日反过来降为**兜底档**（打分罚分而不是禁止，否则假期里有缺口的班永远补不满）。
- **优先补在计划格子上**（`source=plan_gap`），落不到格子的转"这一周任意空闲时段"（`free_cell`）。所以按课时目标统计时，补出来的日期对得上目标、节次可能与周期计划不同。
- **教师与教室取自该班启用中的计划**，多个计划口径不一致时**不猜**，整班退回给操作员（`failures` 里给出中文原因），因为补哪一批都可能排错。
- **同步跑完**，不起异步任务、不加 running 锁：一批几十节在请求超时内跑得完，加状态端点只会多一份要维护的状态机。
- 补不上的会给出中文原因（无空位 / 教师本周或当天已满 / 命中禁排 / 整班退回），在响应的 `failures` 与批次行的 `failure_json` 里，不做静默丢弃。**原因是按"班×周"记的**：某一周第一节排不下去就整周停止尝试，所以 `unscheduled_count`（= 待补 − 已生成）可能大于原因条数，两个数各说各的，界面上会把差额标出来。整班退回（多计划教师/教室口径不一致、没有启用中计划）的那批班根本不进缺口合计，只在原因里出现。
