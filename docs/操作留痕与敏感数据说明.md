# 操作留痕(审计日志)功能说明

> 适用范围:后端写操作(POST/PUT/DELETE/PATCH)与登录/登出会自动留痕,GET 查询不记录。
> 操作日志落库到**独立日志库 `jiaopei_log`**,与业务库(`jiaopei_platform`)完全分离。

## 一、存储架构

- **业务库**(`jiaopei_platform`):存业务数据、权限、菜单。菜单/权限迁移在主 Flyway(`backend/app/src/main/resources/db/migration/`)。
- **日志库**(`jiaopei_log`):操作留痕数据,只增不改,无逻辑删除。由**第二个 Flyway 实例**管理,迁移脚本在 `backend/app/src/main/resources/db/audit-migration/`。

核心表:`oper_log`

| 字段 | 说明 |
|---|---|
| trace_id | 请求链路 ID(对应 `X-Trace-Id`,可用于与业务日志关联) |
| user_id / username / org_id / portal | 操作人、机构、端口(admin=管理后台 / student=学生 / parent=家长) |
| operation | 操作名称(取自 Controller 的 `@Operation(summary)`) |
| action_type | CREATE / UPDATE / DELETE / LOGIN / LOGOUT / OTHER |
| method / path / client_ip / user_agent | 请求信息 |
| params | 请求参数 JSON,**敏感字段已脱敏**(手机号/身份证/银行卡/密码等打码) |
| error_msg | 异常信息(失败时记录) |
| success / duration_ms / created_at | 结果、耗时、操作时间 |

## 二、双数据源与建库

后端通过 `com.jiaopei.platform.config.AuditDataSourceConfig` 配置日志库独立数据源:

- 独立 Hikari 连接池(默认复用业务库的 MySQL 实例与账号);
- 独立 MyBatis-Plus `SqlSessionFactory`(含分页插件),audit Mapper 单独扫描;
- 独立 Flyway,自动执行 `db/audit-migration/` 下的迁移。

### 建库方式

MySQL 官方镜像的 `MYSQL_DATABASE` 只能建一个库,第二个库(日志库)通过挂载初始化脚本自动创建:

- `docker/mysql-init/01_create_databases.sh` 创建 `jiaopei_log` 库,并按需把业务账号授权给它;
- 开发/生产 compose 均已挂载 `./mysql-init:/docker-entrypoint-initdb.d`。

本地已有环境(非 Docker)需手动建库:

```sql
CREATE DATABASE jiaopei_log DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
```

### 日志库连接配置(环境变量)

| 环境变量 | 默认值 | 说明 |
|---|---|---|
| `DB_AUDIT_HOST` | `127.0.0.1` | 日志库主机(容器内为 `mysql`) |
| `DB_AUDIT_PORT` | `3306` | 端口 |
| `DB_AUDIT_NAME` | `jiaopei_log` | 库名 |
| `DB_AUDIT_USERNAME` | `root`(本地)/ `jiaopei`(生产) | 账号,默认复用业务库账号 |
| `DB_AUDIT_PASSWORD` | `1234`(本地) | 密码,默认复用业务库密码 |

> 日志库账号需要有 `jiaopei_log` 库的建表(DML/DDL)权限,因为 Flyway 要建表、切面要写数据。
> 日志库不可用时:启动阶段只告警不阻断;写入阶段异常被隔离,只丢日志、不影响业务接口。

## 三、留痕范围与实现方式

### 自动拦截(无侵入)

`com.jiaopei.platform.audit.aspect.OperateLogAspect` 通过 AOP 自动拦截所有 `@RestController` 方法:

- **记录**:HTTP 方法为 POST / PUT / DELETE / PATCH 的请求 + 登录 `/api/auth/login` + 登出 `/api/auth/logout`(含微信小程序登录)。
- **不记录**:GET / OPTIONS 等查询、健康检查等。

### 操作名与类型

| 来源 | 优先级 |
|---|---|
| `@OperateLog(value = "...", actionType = ActionType.UPDATE)` 显式注解 | 最高 |
| `@Operation(summary = "创建课程")` | 自动取 |
| 降级结果("POST /api/...") | 兜底 |

操作类型默认按 HTTP 方法推断(POST→CREATE, PUT/PATCH→UPDATE, DELETE→DELETE),登录/登出单独识别。

### 跳过留痕

对无需留痕的接口(如健康检查、轮询),在 Controller 方法上标注:

```java
@IgnoreOperateLog
@GetMapping("/api/health")
public ApiResponse<Void> health() { ... }
```

### 敏感参数脱敏

请求参数序列化后经 `com.jiaopei.platform.common.security.JsonSensitiveProcessor` 递归脱敏再落库:

- **按字段名识别**:手机号(`phone`/`mobile`/`tel`…)、证件号(`idCard`/`idNo`/`governmentNo`…)、银行卡(`bankCard`/`cardNo`…)、密码(`password`/`secret`/`accessKey`…)、邮箱(`email`)、人名(`realName`/`parentName`/`studentName`…)、地址(`address`)。字段名大小写/驼峰自动归一(`realName` → `real_name`)。
- **按值格式兜底**:未被字段名命中但值符合 11 位手机、18 位身份证、13~19 位卡号、邮箱格式的,也会脱敏。
- 业务名称字段(如 `courseName`、`className`)不会被误伤。

脱敏示例:`138****1234`、`110***********4512`、`6222 **** **** 0123`、`张*`。

## 四、敏感数据加解密/脱敏工具(通用能力)

`com.jiaopei.platform.common.security` 包提供一套可复用的敏感数据工具,后端任何模块可用:

| 组件 | 说明 |
|---|---|
| `SensitiveType` | 敏感类型枚举(PHONE/ID_CARD/BANK_CARD/PASSWORD/EMAIL/NAME/ADDRESS/OTHER) |
| `DataMasking` | 不可逆打码工具(`mask(value, type)`) |
| `SensitiveCipher` | 可逆对称加密(AES-GCM),`encrypt` / `decrypt`,密文带 `enc:v1:` 前缀 |
| `SensitiveStrategy` | 处理策略:`PLAIN`(不变)/ `MASK`(仅脱敏)/ `ENCRYPT`(加密可解密)/ `ENCRYPT_MASK`(加密存储+展示脱敏) |
| `JsonSensitiveProcessor` | 递归处理请求参数 JSON,MASK 策略即日志用 |
| `@SensitiveField` | 实体/DTO 字段级敏感标注(预留 Jackson 序列化扩展点) |

### 数据密钥

`jiaopei.security.data-key`(环境变量 `DATA_ENCRYPT_KEY`)供 `SensitiveCipher` 使用,经 SHA-256 派生为 AES-256 密钥。**生产必须配置独立强随机串**,不要与 JWT 密钥相同:

```
# 生成:openssl rand -base64 48
DATA_ENCRYPT_KEY=your-strong-random-key
```

> 操作日志落库当前使用 `MASK`(只脱敏、不加密)。为保障「加密、解密、加密且脱敏、脱敏、不变」全套能力,工具层已具备 `ENCRYPT` / `ENCRYPT_MASK` 与解密接口;后续按需对业务字段启用加密存储。

## 五、查询入口(管理后台)

- 后端接口:`GET /api/system/operlogs`,权限码 `system:operlog:read`,筛选:操作人/操作类型/端口/操作名/时间范围/成败,时间倒序分页。
- 前端页面:「系统设置 → 操作日志」(`/system/operlogs`),菜单在前端加载时由 `sys_menu`(V32 迁移已插入)动态提供。

> 查询接口本身不写日志(读操作不入库),避免日志查询刷屏。

## 六、数据量治理(后续)

操作日志只增不改,数据量会持续增长。后续可按需:

- 保留策略:按月归档或删除过期的 `oper_log` 数据;
- 按 `SYSTEM` 定时任务清理 `created_at` 早于保留期的记录;
- 独立日志库方便整体迁移归档,不影响业务库。

## 七、变更涉及文件

- 后端新增:`audit/*`(注解/切面/实体/Mapper/服务/控制器/DTO)、`common/security/*`(敏感工具)、`config/AuditDataSourceConfig`、`config/AsyncConfig`。
- 迁移:业务库 `V32__grant_operlog_permission_and_menu.sql`;日志库 `audit-migration/V1__create_oper_log_table.sql`。
