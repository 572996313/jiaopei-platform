# 底座数据字典与可维护性方案

> 状态：**第一期已落地（2026-11-24，菜单 V116 / core V119，接口 `GET /api/system/schema-dictionary`）**。目标读者是**实施 / 运维工程师**：能在客户现场读懂这套库、找到每个字段的含义与维护入口，尽量不写代码完成日常维护。
> 现行口径以 AGENTS.md 为准；本文只回答"底座怎么让人看懂、看懂到什么程度、哪些还必须找开发"。

## 1. 要解决的问题

用户 2026-11-24 口径：**"让底座变成普通人也能看懂的，能学会数据库、学会每个字段的功能，最终不写代码也能维护底座的功能。"**

现状不是缺资料，是资料散且不可达：

| 已有资产 | 问题 |
| --- | --- |
| 50+ 张表、全部字段的中文 `COMMENT`（AGENTS.md 硬约定） | 躺在 100 多个 Flyway 脚本里，非技术人员永远打不开 |
| 实体 / DTO 的 `@Schema(description=...)`、Controller 的 `@Operation` | 只对开发有意义，且与 COMMENT 无交叉校验 |
| Swagger UI（`/swagger-ui.html`） | 面向开发，满屏英文路径与 JSON |
| `sys_dict_*` 字典管理页 | 管的是**枚举值**，不是表字段；与本方案的"数据字典"撞名 |
| `docs/核心实体清单.md` | 124 行，只有表名 + 一句话，无字段级内容 |
| 后端 `INFORMATION_SCHEMA` 使用 | **零处**——没有任何自动生成的数据字典 |
| `ConfigurableCrudPage` | 只驱动 3 个页面（用户/角色/系统参数），业务页仍旧写死 |

## 2. 结论：四层能力，分期做

| 层 | 解决什么 | 状态 |
| --- | --- | --- |
| 1. 数据字典页 | **看得懂**：表 / 字段 / 类型 / 必填 / 注释 / 主键，可搜索，自动生成 | 本期 |
| 2. 字段 → 页面反查 | **找得到**：这个字段出现在哪个页面、改了会牵连什么 | 二期 |
| 3. 配置化扩面 | **改得动**：列表列 / 筛选 / 按钮 / 表单字段不写代码可改 | 三期 |
| 4. 教学路径 | **学得会**：5 个点鼠标就能做完的练习，全程不出现 SQL | 三期 |

**先做第 1 层**：零新表、只读、当天可用、失败也不污染数据。第 2 层需要手工维护一张 `sys_schema_note`，等第 1 层被真实使用后再决定要不要付这份维护成本。

## 3. 数据来源（唯一事实源，不手写）

**绝不手写数据字典。** 本仓库自己的历史就是证据：V38 半实施事故、collation 归因连改两次，都是手写文档漂移的代价。所有内容从运行时读取：

| 内容 | 来源 |
| --- | --- |
| 表名 / 表注释 / 字段 / 类型 / 可空 / 默认值 / 主键 / EXTRA | `INFORMATION_SCHEMA.TABLES` + `INFORMATION_SCHEMA.COLUMNS`（`TABLE_SCHEMA = DATABASE()`） |
| Java 字段名 / 类型 / `@Schema` 描述 / `allowableValues` | 运行时扫 `@TableName` 实体，反射字段 |
| 所属模块 | 实体的包名（`com.cornerstone.core.*` → core；`.module.<x>.*` → x） |
| 维护入口（去哪个页面改这批数据） | 代码侧 SPI 登记，见 §4 |

字段名匹配规则：`@TableField("列名")` 优先，否则驼峰转下划线（与 MyBatis-Plus 的 `map-underscore-to-camel-case` 一致）。`@TableField(exist = false)` 跳过。

## 4. 维护入口是这一期真正的价值点

用户的原话是"**不需要写代码也能维护**"。所以每张表旁边直接给出去哪改：

| 表 | 维护入口 |
| --- | --- |
| `sys_dict_type` / `sys_dict_item` | 系统设置 → 字典管理 |
| `sys_menu` | 系统设置 → 菜单管理 |
| `sys_list_config` | 系统设置 → 列表配置 |
| `sys_system_config` | 系统设置 → 系统参数 |
| `sys_data_source` | 系统设置 → 数据源 |
| `sys_code_rule` | 系统设置 → 编号规则 |
| `sys_file` | 系统设置 → 文件管理 |
| `sys_user_account` / `sys_role` / `sys_role_menu` / `sys_role_data_scope` | 系统设置 → 用户管理 / 角色管理 |
| 业务表 | 由各业务模块的 Contributor 登记 |

登记走 SPI（镜像 `ActionCatalogContributor` 的既有写法）：底座定义接口与合并逻辑，模块实现并注册 Bean，**core 不 import 任何业务包**。模块关闭时入口随之消失，页面显示"该表由已停用模块维护"。

## 5. 页面设计

位置：系统设置 → **数据字典**（`/system/schema-dictionary`）。**不要叫"字典"**，页面副标题写死一句「这里看表结构与字段含义；枚举值维护在『字典管理』」。

D 型只读页（`docs/前端页面开发手册.md` §4）：左侧模块分组表清单 + 右侧字段详情，两块各自封顶内滚，首屏不用滚轮。

- 顶部统计卡：表数量 / 字段总数 / 无注释字段数（后者应为 0，非 0 即违规）
- 搜索：表名、字段名、**中文注释**三者一起匹配（搜「课时」能定位 `jp_class.total_lessons`）
- 字段行同时显示：数据库注释（权威）+ Java 字段名 + `@Schema`。**两者措辞不同只作浅色附注、不做告警**——实测 814 个字段里有 171 个措辞不同（`0/1` 与 `false/true`、标点、补充说明），逐个标红只会变噪音；真正要拦的是"缺注释"，那个已经红了
- 每张表头部带「维护入口」按钮，直接跳到可改页面

## 6. 必须提前说死的边界

| ✅ 不写代码能改 | ❌ 必须写代码 |
| --- | --- |
| 列表显示哪些列、标题、宽度、排序 | 排课冲突判定 |
| 筛选条件、按钮显隐与文案 | 计费公式、课时换算 |
| 弹窗表单字段、必填、校验 | 权限数据范围、跨表一致性校验 |
| 菜单、字典项、系统参数、编号规则 | 新表 / 新字段（**schema 变更一律走 Flyway**） |

一句话：**展示与录入层可以无代码，算账与校验层不行。** 页面底部常驻这句，避免实施人员对能力产生错误预期——承诺超出能力范围比不做更伤信任。

## 7. 已知缺口（本期不做，写明防误解）

1. **日志库缺失**：`oper_log` 在独立的 `jiaopei_log` 库，主库 `INFORMATION_SCHEMA` 看不到。二期复用 `AuditDataSourceConfig` 的数据源补上。
2. **无字段级业务语义**：DB COMMENT 说明"是什么"，说不清"改它会怎样"。二期用 `sys_schema_note` 补，且只填后果，不重复注释。
3. **无实体/接口映射**：数据字典本期只到表与字段；独立的「接口链路」页已把接口、服务与表接起来（见 `接口链路与系统运作说明.md`），数据字典表头可点「看接口」带表名跳转。
4. **无数据量统计**：`COUNT(*)` 有性能风险，本期不做。

## 8. 验收

2026-11-24 本机实测：**51 张表 / 814 个字段 / 缺注释 0**（模块分布 core 15、education 30、organization 6）。
本期顺带补了唯一一处合规缺口：`jp_student.user_id` 在 V30 加列时漏写 `COMMENT`，由 **V117** 补上（页面统计从 1 变 0）。

- 打开页面能看到全部业务表与字段，中文注释与库内 `COMMENT` 一致
- 搜「课时」「校区」能直接定位到对应字段
- 未写注释的字段在页面被标红（当前为 0）
- 实施人员不看代码，能从页面找到"字典值去哪改、菜单去哪改、参数去哪改"
- 页面在 1294×729 内容区内免滚轮可达（D 型判据）

**发布注意**：权限快照在登录时写进 JWT 与 Redis 会话，新码 `system:schema:read` 对**已登录的旧会话无效**——发布后需重新登录一次，否则菜单能看到、点进去 403。
